# 直接リモートアクセス

直接アクセスは、サーバーパスワードを使って CodeNomad の HTTP/HTTPS リスナーに接続します。[リモートコントロール](remote-control.md)とは別です。ペアリングには LAN バインドや受信ポートは不要で、どちらの経路も他方へ無断でフォールバックしません。

## アクセス経路を選ぶ {#access-paths}

| 経路 | 管理する内容 |
| --- | --- |
| 同じマシンのブラウザー | ループバックへのバインドを維持し、表示されたローカル URL を使用します。 |
| LAN または VPN | 到達可能なインターフェースにバインドし、ファイアウォールを意図したクライアントに限定し、信頼された HTTPS を使用します。VPN は CodeNomad のリスナーを設定しません。 |
| SSH 転送 | バックエンドをループバックにバインドしたまま、実際に表示されたポートを転送します。トンネルは通信を保護しますが、CodeNomad の認証の代わりにはなりません。 |
| リバースプロキシ | バックエンドをプライベート／ループバックインターフェースに置き、プロキシで信頼された TLS を終端し、上流接続を保護します。長時間の SSE と、直接アクセスのツールが必要とする WebSocket に対応させます。 |
| リモートコントロール | ホストから端末をペアリングします。画面の制限と寿命は、[リモートコントロール](remote-control.md)を参照してください。 |

バインドは、ファイアウォールルール、ポート転送、DNS、VPN を作成しません。未認証の HTTP リスナーをインターネットに公開しないでください。ワークスペースルートはセキュリティサンドボックスではありません。サーバーを公開する前に[セキュリティ](security.md)を読んでください。

## 直接アクセスを有効にする {#enable-direct-access}

1. ホストで **設定 → リモートアクセス** を開き、**直接アクセス（ローカルネットワーク、上級者向け）** を展開します。
2. **サーバーパスワード** で **パスワードを設定** または **パスワードを変更** を選び、**新しいパスワード** と **パスワードの確認** を入力して **パスワードを保存** します。起動時指定のパスワードはここでは変更できません。[セキュリティ](security.md)を参照してください。
3. **リッスンモード** の **他の IP からの接続を許可** をオンにします。再起動の警告を読み、一時的な中断の準備ができた場合にのみ **今すぐ再起動** を選びます。
4. 再起動後に **更新** し、**到達可能なアドレス** を確認します。別端末で到達可能な HTTPS アドレスを開くか、ホストで **QR を表示** して別端末で読み取り、ログインします。

これはホストの直接リッスンモードの変更であり、1 つのプロジェクトやリモートコントロールの変更ではありません。サーバーが localhost 以外で待ち受けている間、この開閉セクションは自動的に開きます。自動再起動が使えなければ CodeNomad を手動で再起動します。スタンドアロン環境では、起動時の `--host` を整合させる必要があります。公開を解除するには、スイッチをオフにして再起動するか、ループバックへのバインドで CLI を再起動します。ペアリング済みのリモートコントロール端末は失効しません。

### リスナーのバインド表 {#binding-matrix}

`--host` の既定は `127.0.0.1` で、`localhost` もそのアドレスに正規化されます。有効なリスナーには次の規則が適用されます。

| 起動／モード | HTTP のバインド先 | HTTPS のバインド先 |
| --- | --- | --- |
| スタンドアロン、HTTPS のみ（既定） | 非公開のループバックリスナーのみ（下記参照） | `--host` |
| スタンドアロン、HTTP のみ | LAN／ワイルドカードアドレスを含む **`--host`** | 無効 |
| スタンドアロン、両リスナー | `--host` に関係なく `127.0.0.1` | `--host` |
| ネイティブデスクトップのバックエンド | ホスト内部用を含め、HTTP リスナーは `127.0.0.1` に維持 | HTTPS 有効時の `--host` |

すべてのバックエンドは、ミッションなど CodeNomad 自身の同梱 OpenCode プラグインのために、`127.0.0.1` 上の HTTP リスナーも維持します。HTTP が要求されていない場合、または要求された HTTP リスナーが `127.0.0.1` や `0.0.0.0` 以外のアドレスにバインドされている場合、バックエンドはランダムな `127.0.0.1` ポートに非公開の HTTP リスナーを追加します。このリスナーは表示されることも接続先アドレスとして提示されることもなく、他のマシンからは到達できず、同じ認証付きアプリケーションを提供します。

具体的な LAN アドレスは、ループバック接続を受け付けるとは限りません。`0.0.0.0` はすべての IPv4 インターフェース、`::` はデュアルスタックのワイルドカードリスナーです。ブラウザーにはワイルドカードではなく、実際に到達可能なアドレスを使用してください。`--host` は IPv6 ゾーン識別子に対応しません。

スタンドアロン HTTPS 環境では、[初期設定手順](security.md)でパスワードを設定してから実行します。

```sh
codenomad --host 0.0.0.0 --https=true --http=false
```

ローカルの信頼されたプロキシの背後などで、ループバック専用 HTTP を使う場合：

```sh
codenomad --host 127.0.0.1 --https=false --http=true
```

ポートを 9898 や 9899 と決めつけないでください。省略時は使用中なら別ポートにフォールバックできます。ゼロ以外の `--https-port`、または HTTP 有効時の `--http-port` を明示するとポートを固定し、バインドできなければ失敗します。`0` は OS の割り当てを要求します。その実行での正規の情報は、表示された **Local Connection URL** と **Remote Connection URL**、および更新した **到達可能なアドレス** です。完全な[サーバー CLI リファレンス](server.md)を参照してください。

## 信頼された TLS を設定する {#tls}

### 独自の証明書を指定する {#custom-certificates}

1. クライアントが実際に使うホスト名または IP を Subject Alternative Names（SAN）に含む証明書を取得します。
2. `--tls-key <path>` と `--tls-cert <path>` の両方を PEM ファイルで指定します。環境で CA チェーン／バンドルが必要なら `--tls-ca <path>` を追加します。
3. CodeNomad を再起動し、クライアント端末で証明書と表示された HTTPS アドレスを確認します。

独自の証明書ファイルは起動時に読み込まれ、CodeNomad が書き換えることはありません。更新と、新しいファイルを読み込むための再起動はユーザーが管理します。`--tlsSANs` は生成証明書を設定するもので、指定済み証明書に名前を追加できません。秘密鍵を保護し、ホストの識別を確認した証明書だけを信頼してください。

### 生成されたローカル CA を使う {#generated-certificates}

HTTPS が有効で鍵／証明書のペアを指定していない場合、CodeNomad は設定ベースディレクトリにローカル CA とサーバー証明書を作成します。

| ファイル | 用途 |
| --- | --- |
| `tls/ca-cert.pem` | 管理するクライアントへ安全に配布する公開 CA 証明書。 |
| `tls/ca-key.pem` | CA の秘密鍵。絶対に配布しないでください。 |
| `tls/server-cert.pem` | サーバー証明書。 |
| `tls/server-key.pem` | サーバーの秘密鍵。絶対に配布しないでください。 |

1. `--tlsSANs "host.example.test,192.0.2.10"` で、クライアント向けの全 DNS 名／IP を追加します。ワイルドカードへのバインドは、SAN 用に全 LAN アドレスを検出するものではありません。
2. バックエンドを再起動し、証明書を生成／再確認します。
3. 信頼できる経路でホスト／CA を確認し、意図した各クライアント／ブラウザーの信頼ストアに **CA 証明書だけ** をインポートします。代わりに、公に信頼された証明書や TLS リバースプロキシも使用できます。

生成されるサーバー証明書の有効期間は 30 日です。起動時に、期限まで 3 日以内、必要な SAN の不足、証明書チェックの失敗、秘密鍵ファイルの欠落があれば更新します。生成 CA は 365 日有効で、期限切れ、証明書チェックの失敗、秘密鍵ファイルの欠落で置き換えられます。置き換え時はサーバー証明書も再発行します。既存の破損、読み取り不能、不一致の秘密鍵は自動修復しません。クライアントは新しい CA を信頼する必要があります。プロセス内で継続的には更新しないため、長期稼働では期限前に意図的な再起動を計画してください。

クライアントに証明書警告が出たら、いったん止めてホスト名、SAN、信頼ストア、有効期限を確認してください。検証を無効にしたり、警告を無視して進むことを運用手順にしたりしないでください。信頼された HTTPS は、[PWA のインストールやマイクアクセス](mobile.md)など、リモートブラウザー機能にも必要です。

## リモートサーバーを保存する {#saved-servers}

1. ホーム、空のタブ、**タブを開く** ランチャーで **参照** を開き、アドレスまたはペアリングリンクを **サーバーのアドレスまたはリンク** に入力します。貼り付けは即座に追加し、手入力は Enter で追加します。サーバーはホスト名で保存され、その行にフォーカスが移ります。ペアリングリンクでは参照用のローカルバックエンドもペアリングします。ランチャーは開いたままです。行をクリックすると、その場でプロジェクトを参照できます。**設定 → サーバー** にも同じ入力欄があります。
2. 信頼できる HTTPS オリジンを使ってください。証明書の検証に失敗した場合、入力欄の下に **TLS 検証をスキップ** が表示されます。信頼できるサーバーだけでオンにして Enter で保存します。このプロファイルのフォルダーやプロジェクトを選ぶと専用ウィンドウで開きます。
3. **参照** の保存済みサーバー行を選ぶと、その場でプロジェクトを参照できます。求められたらインラインフォームにユーザー名とパスワードを入力します。名前やアドレスは **設定 → サーバー** の **サーバーを編集** で変更できます。

**設定 → サーバー** でプロファイルを管理します（**サーバーを編集**、**保存したサーバーを削除**）。削除時は、まずバックエンドの参照用認証情報とセッションを消去し、ブックマークを削除して関連タブを閉じます。リモートのプロジェクトと会話はサーバーに残ります。ローカルバックエンドは参照用の秘密情報を設定の隣の `remote-server-credentials.json` に保存します。このファイルはパスワードと同様に保護してください。埋め込みビューの認証は独立しています。

保存したサーバーをコマンドラインから直接開くには、サーバーの保存名か `https://` URL を指定して、デスクトップアプリを `--connect-server <name>`(または `--connect-server=<name>`)付きで起動します。CodeNomad はリモートウィンドウだけを開き、プロファイルの TLS 検証とネイティブリモートウィンドウ独自のサインインを使います。CodeNomad がすでに起動している場合は、新しいウィンドウではなく現在のウィンドウから開きます。どの保存済みサーバーにも一致しない URL は、ホスト名で保存されます。起動時の値に認証情報は含められません。ユーザー名、パスワード、ペアリングコードを含む URL は拒否されます。名前が不明な場合、URL が無効な場合、または接続に失敗した場合、CodeNomad は通常どおり起動してエラーを表示します。 自己署名サーバー用のローカル証明書のインストールなど、接続に確認が必要な場合も、CodeNomad は通常どおり起動してそこで確認します。 Windows では、起動引数に `|` が含まれると Tauri 版は起動しません。代わりにサーバーの URL を使うか、サーバー名を変更してください。

リモートウィンドウからは、いつでもこのコンピューターに戻れます。リモートウィンドウを開いたまま最後のローカルウィンドウを閉じても、そのタブは保持されます。リモートウィンドウの **ウィンドウ → 新規ウィンドウ**、または CodeNomad の再起動で再び開きます。サーバーを読み込めない場合は、そのウィンドウにその旨が表示され、**再試行**、**ローカルウィンドウを開く**、**ウィンドウを閉じる** を選べます。Tauri 版では、ページの再読み込みボタンと **ウィンドウ → 新規ウィンドウ** を使用します。

新しいリモートコントロールのリンクを貼り付けると、トンネルのオリジンを保存し、参照用のローカルバックエンドをペアリングします。デバイス認証情報は非公開で再起動後も保持され、コードは試行後に破棄されます。取り消し後は **参照に戻る** を選び、新しいリンクを **サーバーのアドレスまたはリンク** に貼り付けてください。埋め込みビューは別途ペアリングします。サーバー側のペアリングが利用できない場合は、リモートサーバーを更新するか、パスワードログインに直接アクセス用リスナーの URL を使ってください。トンネルアドレスにはペアリングが必要です。[リモートコントロール](remote-control.md)を参照してください。

## リモートプロジェクトをタブで開く {#remote-project-tabs}

デスクトップアプリ（Electron、または Windows の Tauri）では、保存済みサーバーのプロジェクトを、ローカルプロジェクトと並べてこのウィンドウのタブで開くこともできます。

1. ホーム、空のタブ、**タブを開く** ランチャーで **参照** を開き、保存済みサーバーを選びます。先に追加する場合は **サーバーのアドレスまたはリンク** を使い、新しい行をクリックします。
2. 一覧がその場でサーバーの最近のプロジェクトとフォルダーに切り替わります。必要ならインラインフォームでサインインします。最近のプロジェクトを選ぶか、フォルダーを移動して **現在のフォルダを選択** を押します。**参照に戻る** でサーバー一覧に戻れます。
3. フォルダーを選ぶとリモートプロジェクトのタブが開き、元の空タブを置き換えます。`+` ランチャーは選択まで開いたままです。プロジェクトは直接開き直せるよう **最近** に追加されます。

タブの会話、ファイル、Git、設定、Missions はリモートサーバーで動作します。埋め込みビューはそのサーバーのリモートウィンドウのストレージを共有し、参照とは別にサインインを求める場合があります。リモートタブは起動時に復元されます。埋め込みモードのないサーバーは完全な UI を表示し、TLS 検証を省略するプロファイルと macOS/Linux の Tauri は別ウィンドウを開きます。埋め込みページはサーバー内に留まり、ホストへは通知のみ送れます。Web クライアントとリモートコントロール端末にはリモートタブはありません。

バックエンド参照は、保存したすべてのプロファイルの接続先アドレスを受け付けます。対象にはループバック、RFC1918 LAN、Docker、Hyper-V、CGNAT/Tailscale（`100.64.0.0/10`）、MagicDNS と `*.ts.net`、IPv6 ULA/リンクローカル、およびこれらのアドレスに解決される名前が含まれます。接続には、ネットワーク経路と TLS 設定が適切に機能する必要があります。証明書検証は保存したプロファイルと明示的な TLS 確認に従います。
