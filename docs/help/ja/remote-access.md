# 直接リモートアクセス

直接アクセスは、サーバーパスワードを使って CodeNomad の HTTP/HTTPS リスナーに接続します。[リモートコントロール](remote-control.md)とは別です。ペアリングには LAN バインドや受信ポートは不要で、どちらの経路も他方へ無断でフォールバックしません。

## アクセス経路を選ぶ {#access-paths}

| 経路 | 管理する内容 |
| --- | --- |
| 同じマシンのブラウザー | ループバックへのバインドを維持し、表示されたローカル URL を使用します。 |
| LAN または VPN | 到達可能なインターフェースにバインドし、ファイアウォールを意図したクライアントに限定し、信頼された HTTPS を使用します。VPN は CodeNomad のリスナーを設定しません。 |
| SSH 転送 | バックエンドをループバックにバインドしたまま、実際に表示されたポートを転送します。トンネルは通信を保護しますが、CodeNomad の認証の代わりにはなりません。 |
| リバースプロキシ | バックエンドをプライベート／ループバックインターフェースに置き、プロキシで信頼された TLS を終端し、上流接続を保護します。長時間の SSE と、直接アクセスのツールが必要とする WebSocket に対応させます。 |
| リモートコントロール | ホストから端末をペアリングします。画面の制限と寿命は、[リモートコントロール](remote-control.md)を参照してください。 |

バインドは、ファイアウォールルール、ポート転送、DNS、VPN を作成しません。未認証の HTTP リスナーをインターネットに公開しないでください。ワークスペースルートはセキュリティサンドボックスではありません。サーバーを公開する前に[セキュリティ](security.md)を読んでください。

## 直接アクセスを有効にする {#enable-direct-access}

1. ホストで **設定 → リモートアクセス** を開き、**直接アクセス（ローカルネットワーク、上級者向け）** を展開します。
2. **サーバーパスワード** で **パスワードを設定** または **パスワードを変更** を選び、**新しいパスワード** と **パスワードの確認** を入力して **パスワードを保存** します。起動時指定のパスワードはここでは変更できません。[セキュリティ](security.md)を参照してください。
3. **リッスンモード** の **他の IP からの接続を許可** をオンにします。再起動の警告を読み、一時的な中断の準備ができた場合にのみ **今すぐ再起動** を選びます。
4. 再起動後に **更新** し、**到達可能なアドレス** を確認します。別端末で到達可能な HTTPS アドレスを開くか、ホストで **QR を表示** して別端末で読み取り、ログインします。

これはホストの直接リッスンモードの変更であり、1 つのプロジェクトやリモートコントロールの変更ではありません。サーバーが localhost 以外で待ち受けている間、この開閉セクションは自動的に開きます。自動再起動が使えなければ CodeNomad を手動で再起動します。スタンドアロン環境では、起動時の `--host` を整合させる必要があります。公開を解除するには、スイッチをオフにして再起動するか、ループバックへのバインドで CLI を再起動します。ペアリング済みのリモートコントロール端末は失効しません。

### リスナーのバインド表 {#binding-matrix}

`--host` の既定は `127.0.0.1` で、`localhost` もそのアドレスに正規化されます。有効なリスナーには次の規則が適用されます。

| 起動／モード | HTTP のバインド先 | HTTPS のバインド先 |
| --- | --- | --- |
| スタンドアロン、HTTPS のみ（既定） | 非公開のループバックリスナーのみ | `--host` |
| スタンドアロン、HTTP のみ | LAN／ワイルドカードアドレスを含む **`--host`** | 無効 |
| スタンドアロン、両リスナー | `--host` に関係なく `127.0.0.1` | `--host` |
| ネイティブデスクトップのバックエンド | ホスト内部用を含め、HTTP リスナーは `127.0.0.1` に維持 | HTTPS 有効時の `--host` |

具体的な LAN アドレスは、ループバック接続を受け付けるとは限りません。`0.0.0.0` はすべての IPv4 インターフェース、`::` はデュアルスタックのワイルドカードリスナーです。ブラウザーにはワイルドカードではなく、実際に到達可能なアドレスを使用してください。`--host` は IPv6 ゾーン識別子に対応しません。

スタンドアロン HTTPS 環境では、[初期設定手順](security.md)でパスワードを設定してから実行します。

```sh
codenomad --host 0.0.0.0 --https=true --http=false
```

ローカルの信頼されたプロキシの背後などで、ループバック専用 HTTP を使う場合：

```sh
codenomad --host 127.0.0.1 --https=false --http=true
```

ポートを 9898 や 9899 と決めつけないでください。省略時は使用中なら別ポートにフォールバックできます。ゼロ以外の `--https-port`、または HTTP 有効時の `--http-port` を明示するとポートを固定し、バインドできなければ失敗します。`0` は OS の割り当てを要求します。その実行での正規の情報は、表示された **Local Connection URL** と **Remote Connection URL**、および更新した **到達可能なアドレス** です。完全な[サーバー CLI リファレンス](server.md)を参照してください。

## 管理者ポリシー {#administrator-policy}

管理者は待ち受けアドレスを固定できます。`CODENOMAD_LOCKED_HOST` にサーバーが使うアドレスをシステム全体で設定し、CodeNomad を再起動します。この設定は `--host`、`CLI_HOST`、**他の IP からの接続を許可** より優先され、スイッチは結果を表示しますが変更できません。同僚が社内ネットワーク経由でサーバーに接続できるようにするにはイントラネットのアドレスを、このコンピューターに限定するには `127.0.0.1` を使います。すべてのアクセスを社内ネットワーク内に留めるには、`CODENOMAD_REMOTE_CONTROL=disabled` も設定します ([リモートコントロール](remote-control.md#administrator-policy))。

## 許可するオリジン {#upgrading}

ホスト名の別名、リバースプロキシ、別途ホストする UI を使う場合は、バックエンドの `CODENOMAD_ALLOWED_ORIGINS` に信頼する UI のオリジン（スキーム、ホスト名、ポート）を設定します。 LAN 上のネイティブクライアントは、変更リクエストに許可された `Origin` ヘッダーを付ける必要があります。 その HTTPS オリジンでは、ホストがトンネルなしで端末をペアリングすることもできます。 [直接 HTTPS でペアリングする](remote-control.md#direct-https)を参照してください。

UI を別途ホストしている場合は、サーバーを更新する前に UI をデプロイし、開いているタブとウィンドウを再読み込みしてください。サーバーが UI を配信する場合は、更新後に再読み込みしてください。

ホスト専用の操作にはループバック接続を使ってください。対象は SideCar のコンテンツ（`/sidecars/`）と WebSocket、リモートコントロールの管理（`/api/remote-control/`）、プラグインブリッジ（`/api/opencode-plugin/`）、リモートプロキシ（`/api/remote-proxy/`）、パスワード変更、トークンによる初期設定です。LAN からの直接アクセスでログイン済みでも、これらにはループバックが必要です。例外は SideCar だけです。ホストの **HTTPS で SideCar を開く** 設定を有効にすると、信頼された HTTPS オリジンからサインインしたブラウザーにそのコンテンツと WebSocket が開放されます（[SideCar](browser-sidecars.md#register-sidecar)）。有効なケイパビリティトークンがあれば、アクティブなプレビューのコンテンツ（`/previews/`）は LAN からの直接アクセスで利用できます。

`/api/sidecars` 登録 API は、認証済みの LAN 直接接続クライアントとペアリング済み端末で引き続き利用できます。リモートコントロールの Web プレビューは、ホストで有効な間、ケイパビリティトークンで利用できます。 認証済みクライアントのサーバー管理と認証情報の安全な入力について： [リモートサーバーを保存する](remote-access.md#saved-servers).

## 信頼された TLS を設定する {#tls}

### 独自の証明書を指定する {#custom-certificates}

1. クライアントが実際に使うホスト名または IP を Subject Alternative Names（SAN）に含む証明書を取得します。
2. `--tls-key <path>` と `--tls-cert <path>` の両方を PEM ファイルで指定します。環境で CA チェーン／バンドルが必要なら `--tls-ca <path>` を追加します。
3. CodeNomad を再起動し、クライアント端末で証明書と表示された HTTPS アドレスを確認します。

独自の証明書ファイルは起動時に読み込まれ、CodeNomad が書き換えることはありません。更新と、新しいファイルを読み込むための再起動はユーザーが管理します。`--tlsSANs` は生成証明書を設定するもので、指定済み証明書に名前を追加できません。秘密鍵を保護し、ホストの識別を確認した証明書だけを信頼してください。

### 生成されたローカル CA を使う {#generated-certificates}

HTTPS が有効で鍵／証明書のペアを指定していない場合、CodeNomad は設定ベースディレクトリにローカル CA とサーバー証明書を作成します。

| ファイル | 用途 |
| --- | --- |
| `tls/ca-cert.pem` | 管理するクライアントへ安全に配布する公開 CA 証明書。 |
| `tls/ca-key.pem` | CA の秘密鍵。絶対に配布しないでください。 |
| `tls/server-cert.pem` | サーバー証明書。 |
| `tls/server-key.pem` | サーバーの秘密鍵。絶対に配布しないでください。 |

1. `--tlsSANs "host.example.test,192.0.2.10"` で、クライアント向けの全 DNS 名／IP を追加します。ワイルドカードへのバインドは、SAN 用に全 LAN アドレスを検出するものではありません。
2. バックエンドを再起動し、証明書を生成／再確認します。
3. 信頼できる経路でホスト／CA を確認し、意図した各クライアント／ブラウザーの信頼ストアに **CA 証明書だけ** をインポートします。代わりに、公に信頼された証明書や TLS リバースプロキシも使用できます。

生成されるサーバー証明書の有効期間は 30 日です。起動時に、期限まで 3 日以内、必要な SAN の不足、証明書チェックの失敗、秘密鍵ファイルの欠落があれば更新します。生成 CA は 365 日有効で、期限切れ、証明書チェックの失敗、秘密鍵ファイルの欠落で置き換えられます。置き換え時はサーバー証明書も再発行します。クライアントは新しい CA を信頼する必要があります。プロセス内で継続的には更新しないため、長期稼働では期限前に意図的な再起動を計画してください。

クライアントに証明書警告が出たら、いったん止めてホスト名、SAN、信頼ストア、有効期限を確認してください。検証を無効にしたり、警告を無視して進むことを運用手順にしたりしないでください。信頼された HTTPS は、[PWA のインストールやマイクアクセス](mobile.md)など、リモートブラウザー機能にも必要です。

## リモートサーバーを保存する {#saved-servers}

認証済みのリモートクライアントは、ローカルクライアントと同じ保存済みサーバーを利用・管理できます。新しいサーバーパスワードやペアリングリンクを入力するには、HTTPS またはリモートコントロールが必要です。

**設定 → サーバー** の **サーバーのアドレスまたはリンク** にアドレスやペアリングリンクを貼り付けるか、入力して Enter を押します。プロジェクトを開かずにサーバーが保存されます。**サーバーを編集** で **URL** や任意の **名前** を変更できます。同じ URL と TLS ポリシーでの名前変更はオフラインでも可能です。確認後、**削除** はこのウィンドウでそのサーバーのタブを閉じ、最近のショートカットを削除します。一時プロジェクトでは **保持** または **破棄** を選びます。**破棄** すると、ファイルと会話が削除されます。ほかのプロジェクトと会話はサーバーに残ります。

CodeNomad のホストには OpenSSH が必要で、接続先では CodeNomad がすでに動作している必要があります。 **設定 → サーバー** で **SSH サーバーを追加** を選びます。SSH ホストから見た CodeNomad の **URL** と **SSH ホスト（任意）** またはエイリアスを入力し、**保存** します。プロファイルはオフラインでも保存できます。OpenSSH には鍵認証と `known_hosts` の検証済みホスト鍵が必要です。接続先の CodeNomad にサインインしてください。HTTPS 証明書も検証されます。

サーバーの編集画面には **TLS 検証をスキップ** のチェックボックスがあります。**サーバーのアドレスまたはリンク** 欄では、そのアドレスで証明書エラーが発生した場合にだけ、このオプションが表示されます。アドレスを変更すると選択は解除されます。ペアリングでは常に TLS を検証します。

`multiBackend` を `false` に設定している場合のみ、以下の手順で別のデスクトップウィンドウを開きます。

1. **設定 → リモートアクセス → サーバー** → **CodeNomad サーバーに接続**.
2. **サーバーに接続** で、信頼された HTTPS オリジンを使用して **サーバー名** と **サーバー URL** を入力します。**自己署名証明書の TLS 検証をスキップします。** はチェックせず、代わりに信頼を確立します。
3. ブックマークには **保存**、保存して開くには **接続** を選び、そのサーバーでログインします。

リモートウィンドウを開いたまま最後のローカルウィンドウを閉じても、そのタブは保持されます。リモートウィンドウの **ウィンドウ → 新規ウィンドウ**、または CodeNomad の再起動で再び開きます。

リモートコントロールでは、代わりに新しいペアリングリンクを **サーバー URL** に貼り付けます。ブックマークはトンネルのオリジンだけを保持し、使い捨てのペアリングコードは保持しません。端末 Cookie 消失後の再ペアリングは、[リモートコントロール](remote-control.md)を参照してください。

## リモートプロジェクトをタブで開く {#remote-project-tabs}

空のタブで **参照** を開き、サーバーを選びます。保存するには **サーバーのアドレスまたはリンク** にアドレスかペアリングリンクを貼り付けます。必要に応じてサインインします。フォルダーをクリックして移動し、パス欄で Enter を押すか **開く** で開きます。**参照に戻る** でサーバー一覧に戻ります。

ローカルとリモートのプロジェクトは同じウィンドウで開きます。参照中のサーバーのショートカットは **最近のタブ** に表示されます。混在一覧では、ここで開いたプロジェクトにサーバーのアイコンと名前が付きます。 [リモートタブの復元](projects.md#restore-remote-tabs)。

**設定 → サーバー** の **開く** は **参照** でサーバーを選択し、すでに開いている空のタブがあれば再利用します。

### `--connect-server` {#connect-server}

`--connect-server <name-or-url>` は `multiBackend` の値に関係なく、別のリモートウィンドウを開きます。保存済みの名前や ID、または HTTP(S) URL を指定します。新しい URL はホスト名で保存されます。起動時の URL にはユーザー名、パスワード、ペアリングコードを含められません。構文とリモートウィンドウだけを開く手順は[デスクトップ起動引数の表](desktop.md#desktop-cli)を参照してください。
