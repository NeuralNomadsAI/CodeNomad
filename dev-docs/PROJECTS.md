# Projects and tabs

## Agent conventions

- The saved-server picker keys its Dialog/Portal by validated profile policy. Same-policy selection preserves intent, lifetime and pending opening; origin/TLS/SSH changes dispose the browser, work and ARIA title before mounting the next dialog. Reselection after cancellation starts fresh.

**Remote opening ownership boundaries**

- Browser/PWA restoration admits each saved backend and reuses its saved record before its backend/folder occurrence. Reload and Retry only bind existing records. Missing primary-backend records retain their own placeholder and drafts independently of the multi-backend flag; Retry reads the primary inventory and recovery consumes that confirmed read even after a startup read failure. Primary and compatible remote placeholders expose explicit Open through the same inventory, commit, draft and uncertain-creation fences; it creates only that missing occurrence. Native local restoration keeps its existing creation policy.

`openRemoteProject` receives an opaque `WorkspaceCreationOwnership` through signal-scoped `createInstance.onCreation` before dispatch. Every untransferred exit runs its idempotent discard, including rejected or resolved-but-obsolete creation. Explicit commits retire older claims for the same UI key; passive observations enrich their current claim. Cleanup and failed-settlement restoration retain the exact request/API/attachment and current occurrence.

| Boundary | Owner | Stale or cancelled outcome |
| --- | --- | --- |
| Existing remote restore placeholder, before admission and after inventory recovery | Saved backend/folder occurrence and its restore queue | Explicit opening selects the waiting tab, preserving drafts and its explicit Retry owner. |
| `await backendRegistry.ensure` | Shared registry admission/client | Current-intent check ends the opening before creation; the registry retains its shared client. |
| `await retryWorkspaces` | Shared inventory flight and captured attachment | Current-intent check ends the opening before creation. |
| `await createInstance` / POST | Captured creation request, API and attachment | Abort, caller-finally and exact-request observations share one cancellation flight and bounded retry budget, including a lost POST response. Definitive route rejection settles the request; uncertain outcomes retain the original responsibility until confirmed cancellation. |
| Response / commit wait | Exact receipt and prospective occurrence | Cancellation joins that same request; publication checks the attachment and commit gate. |
| Resolved create continuation | Exact committed occurrence and receipt | Caller-finally discards the captured claim. UI removal matches its current request key; retired cleanup preserves replacement occurrences. |
| Synchronous tab selection → release ACK | Guarded occurrence transfers to its tab; release retains the captured API/request key | Selection rechecks ownership and reports successful transfer. Subsequent intent changes preserve the adopted tab; release completes or retains its exact retryable claim. |
| Native selection reply | Correlated profile-selection ticket and exact opener | ACK, refusal or timeout consumes its matching ticket. Current browsers and adopted tabs follow their own ownership lifetimes. |

- Abort, continuation and caller-finally share one discard flight and bounded retry budget. Later discard/exact-request observations resume failed cancellation on the captured API/attachment/request key. Keep uncertain receipts quarantined until confirmed settlement; preserve replacement projections and reused records while cancelling only the captured request.

- Experimental multi-backend opening (`remote-project-open.ts`, `remote-server-browser.tsx`) captures immutable saved policy and rechecks it before admission/publication. `backendRegistry.ensure` supplies the exact `createInstance` client. Browse, typed paths and remote recents share ordinary instance tabs with server icon/name, including duplicate labels; Clone/Temporary keep their local home-page owner. Incompatible metadata and HTTP 426 refuse admission.

- Connection removal and retargeting require confirmation after the usage check succeeds. The confirmation covers saved tabs in other windows whose drafts outlive the remote workspace inventory.

- Settlement, terminal events and delayed callbacks retain the receipt's exact attachment/request. Confirmed release/cancellation/stop drops its descriptor and client/API/attachment references; definitive create rejection ends the receipt. Transport failure, abort, uncertain server errors and revoked claims retain their owner for retries. Settled slots keep primitive duplicate-response fences; cancelled occurrences keep event tombstones until explicit opening.
- List/SSE ingestion checks backend/attachment/request cancellation fences before first publication. Capture cancellation and explicit opening order before dispatch; confirmed cancellation applies that immutable order, preserving later user ownership regardless of response order. Reused observations retain user ownership. Stop can settle an in-flight release; delayed HTTP completion checks the settled slot.

- `createInstance` accepts an explicit backend client and otherwise uses the local backend. Remote admission requires the strict multi-backend flag, the registered client, its live attachment and its bound relay proof. Capture a memory-only operation receipt before POST or queued close: backend, exact client/API, attachment, physical directory and raw creation request id; response descriptors add raw workspace id and qualified UI key. List and SSE enrichment preserve that receipt. Creation callbacks, publication and failed-cleanup restoration recheck its attachment, while claim cancel/release retries retain the original API independently of caller cancellation. Refused settlement preserves its unknown claim and never selects a replacement client. Commit gates match request ids and physical paths within one backend; DELETE/release decode the UI key once at the HTTP adapter. Temporary and ordinary local entry points keep their local owner. With multi-backend enabled, saved remote tabs admit their owner through `ensure`, then reuse or create occurrences in the existing restore queue. Unavailable owners retain an ordered, selectable `remote-restore` tab carrying the complete saved workspace state.
- Remote placeholders offer per-server Retry and inline Connect with credentials or a fresh pairing link. Retry shares a per-backend flight, revalidates inventory through `retryWorkspaces` and restores only still-open placeholders, independently of the automatic startup restoration preference. Reconciliation preserves each live or suspended tab's workspace binding; an inventory position belonging to a sibling stays reserved, and a definitively refused missing occurrence can be created again. Close revokes the saved occurrence's creation guard. Uncertain remote creates remain parked for inventory reconciliation; explicit HTTP refusals allow a fresh attempt. Session recovery retains its read-only contract. Non-authoritative removal captures live tabs before releasing sessions; placeholders reserve their folder occurrence while siblings disappear. Profile removal and target changes check tabs/drafts and authoritative remote workspace inventory, refusing unavailable checks. Names may change in place.
- Explicit Retry/successful connection calls `backendRegistry.retryWorkspaces(profileId)` with the admitted client and captured attachment, revalidating metadata/identity/relay proof before reading. Concurrent demands share one flight; `{ invalidate: true }` admits one serialized follow-up, then parks until new demand. Failure rejects while retaining the display snapshot; `ensure` keeps its coalesced admission.
- Metadata verdict and inventory availability have separate authority. Connection gates follow the latest verdict; inventory publication retains attachment and metadata-failure epoch across reconnects. Only a current published inventory repairs inventory failure; intervening metadata failure fences success. Recovery/reconnect share the backend's list reconciliation and creation/cancellation/opening fences. Propagate `false` for skipped/superseded reads.
- Host Git probes report `git_required` only for an absent executable (`ENOENT`). Timeouts, killed processes, unsuccessful exits and invalid version output yield `git_probe_unavailable` (503, retryable); the availability advisory propagates uncertainty to its best-effort caller rather than publishing installation guidance. The probe retains its five-second deadline and rechecks on demand.

- Closing a project tab detaches it immediately and requests deletion of that occurrence's logical backend workspace record; failures notify and never retry automatically. Separate occurrences of the same folder are independent. A `workspace.stopped` deletion closes the same record in other windows and notifies only windows displaying it that did not initiate the close. CodeNomad never evicts native Locations; OpenCode sessions keep running and reopening finds them. Whole-window close, app quit, renderer reload and backend shutdown keep existing restoration behavior. Temporary discard and server stop events use local-only tab detachment, not another DELETE; Keep closes the retained project normally.
- A suspended remote occurrence keeps its drafts and attachments in its own saved placeholder snapshot. Removing its live instance returns only unapplied closed-draft claims; normal placeholder Close hands the snapshot to the backend/folder draft vault through `RemoteRestoreTab.remove`, while successful Retry consumes its own snapshot. Restored occurrence state takes precedence over closed sibling drafts. Temporary-folder discard authority follows each backend's current event attachment and resets on its reconnect or detach.
- Restorable workspace descriptors carry an optional versioned `viewState` envelope. `stores/tab-view-state.ts` owns its runtime copy by instance UUID; capture writes each occurrence's envelope alongside its own descriptor, and hydration seeds it onto the restored UUID before selecting a conversation. Repeated hydration preserves local gestures. Runtime tab bindings keep views attached through reorder and partial restore; explicit removal clears only that occurrence, while backend unavailability preserves recovery state. The envelope carries per-session preview URLs/mode/history/viewport, Mission reader/selection/expanded rows/disclosures, right-panel selection and Files mode. Consumers read `getTabViewState`, replace individual fields with `updateTabViewState` and reserve `seedTabViewState` for restoration; capture's optional accessor preserves unhydrated fallback state. Seeded Mission reader targets bind their instance references to the restored UUID. See [the restore payload](architecture.md#native-profiles-windows-and-client-state) for its storage contract.
- Client-state initialization adopts bounded folder/session preview entries into every matching saved descriptor. A project-wide URL belongs to the first matching descriptor with a saved conversation, in descriptor order. Versioned envelopes retain authority over imported values, including empty views. Unmatched folders remain eligible for migration; consumed entries retire after successful snapshot publication, with concurrent legacy writes fenced by their original value. Browser tabs publish migrated browser/Mission views in their sessionStorage snapshot while shared layout preferences stay in localStorage. Restoration seeds data only; a preview consumer must explicitly open its saved URL. Preview persistence shares a 4,000-character budget across the window's descriptors (active descriptor first), with 32 previews per descriptor and 32 credential-free HTTP(S) history entries per preview; history trims before preview eviction.
- Unsent drafts and attachments outlive their project tab in the window's memory (`stores/closed-workspace-drafts.ts`). `removeInstance` hands them over just before clearing them, keyed by project identity (`closedWorkspaceDraftKey`: backend id, empty for the window's own backend, plus the `normalizeWorkspacePath` folder), for every removal: user close, a close from another window, a backend stop or restart reconciliation. Temporary discards (`drafts: "discard"`) keep nothing and purge the project's whole entry, drafts and attachments, because the folder is deleted. Every window recognizes them: the server deletes a discarded record (`workspace.stopped` with reason `deleted`) before unregistering its folder, whereas Keep unregisters first, so a deleted record whose folder the latest `workspace.temporaryChanged` still lists was discarded. That registry state is the only authority: the instance's `temporary` mark can be stale (a workspace-list response requested before Keep, a Keep missed while disconnected). Without a broadcast on the current event connection (none yet, or reset on reconnect) no removal is a discard and the drafts are kept, since an entry for a deleted folder is harmless and bounded while dropping a kept project's drafts loses work. Restoration-owned instances discarded by `removeRestoreCreatedInstanceFromUi` keep nothing either (`drafts: "skip"`; restoration still holds what it seeded). Closing several occurrences of a folder merges them, the later close replacing a session's text and attachments together, including a session it emptied by typing, clearing or sending (draft/attachment authority with no content), which removes the older value. A close supersedes those sessions both in the vault and in every pending restore of the project (entries taken by a reopened tab whose restore has not finished), because a pending restore is the only way older drafts return to the vault; the vault therefore stores no clear marks, and another reopening cannot consume one. `addInstance` takes the entry once for that identity and hydrates it through `hydrateWorkspacePromptState`, only into sessions the instance shows nothing for and the user has not touched, so occurrence-aware startup, web or reconnect restoration and the user's own typing always win: the new-conversation draft at once, session drafts after `waitForInstanceInitialSessionHydration` plus `hydrateRestoredSessionChain` for their sessions, so missing sessions get nothing. Filling empty sessions can copy one occurrence's draft into an empty, untouched session of another occurrence of the folder; nothing is overwritten. A restore that fails, or whose tab closes before it finishes, puts back underneath only the sessions it could not apply and the user did not touch there. At most 16 projects are kept, least recently closed evicted first; nothing is persisted, so desktop and web restoration stay the only mechanisms across reloads.
- Git is a full-functionality prerequisite, with directory-only degraded conversations when the backend cannot find Git. Only the explicitly opened physical folder is session authority in that mode; never infer sibling worktrees from native project IDs. Keep ancestor/descendant mutation identities covered by the deletion fence across Git availability changes. Inform agents through the owned native `codenomad.git-availability` instruction before prompts/custom commands, remove stale context after recovery, and keep this advisory separate from fail-closed environment synchronization. Do not add a blocking Git setup UI. Validate with `scripts/test-git-degraded-native.mjs` using an isolated CLI/database and provider.
- Temporary instances (`workspaces/temporary-workspaces.ts`, UI `stores/temporary-instances.ts`) are ordinary non-Git workspaces on CodeNomad-created direct children of `<config>/temporary-workspaces`. Registry membership (`temporary-workspaces.json`), not location, makes a folder temporary; keeping only unregisters it and adds a named recent project. Discard deletes only registered children of that root, refuses running conversations and other open tabs of the folder, removes conversations deepest-first, closes the workspace before deleting the folder and keeps failed removals registered; such a folder is reachable only by browsing to it. Closing a temporary tab from the UI asks Keep/Discard/Cancel, except that an untouched one (no conversation, file or unsent draft) closes and is discarded silently (`onlyIfEmpty`: the server refuses with `temporary_has_conversations`/`temporary_not_empty`, and any failure of that quiet discard returns the choice without an error). Before the server stops it, a visible temporary tab yields to its neighbour (or closes if alone) and a refusal restores it in place; `workspace.stopped` likewise closes the tab first and clears the instance in a microtask, because clearing a visible shell's state in the same update as its tab freezes the window. Same-minute names get a `(n)` suffix. Registry changes broadcast `workspace.temporaryChanged`, which clears kept marks in every window. Open temporary tabs are saved and restored with the app state like any project tab (still marked temporary). Only the choice dialog overrides initial focus (to its last, non-destructive choice); confirms keep focus on Cancel. Refusals use stable `temporary_*` codes localized by the client. Validate with `scripts/test-temporary-workspaces-native.mjs` against an isolated CLI.
- The tab-bar new-instance button follows the last tab like a browser: the instance `TabScroll` frame only spans its tabs and the button sits after it, outside the scroller (so focusing it never scrolls the strip), ending up at the strip's end once tabs overflow. Dragged tabs stay visually within the tab list like a browser's (`KeepDraggedTabInStrip`), while the drop slot follows the pointer's unbounded position (`closestUnboundedCenter`). The button keeps its click (full home page, Cmd/Ctrl+N) while a long press, right-click, Alt+Down, Shift+F10 or Menu opens the anchored `NewInstanceLauncher` (`lib/long-press.ts`; only Escape returns focus to the button, never over another surface or the home page): search-first recent projects (an open project switches to its tab) and Browse/Temporary/Clone only. Remote servers, SideCar and management (rename/remove recents, servers, settings) stay on the home page. Browse/clone flows live once in `components/new-instance-dialogs.tsx` (with optional home-only add-server setup) and recent-folder display helpers in `lib/recent-folder-display.ts`, shared with `FolderSelectionView`; styles in `styles/components/new-instance-launcher.css`.
- The clone dialog (`components/new-instance-dialogs.tsx`) suggests the repository's `git clone` folder name (`lib/clone-destination.ts`) inside a parent: the folder chosen with Browse, else the server-scoped `ui` state `lastCloneParent` (the folder above the last successful clone), else the folder above the most recent project. A destination the user types is kept as entered and sent unchanged; the server creates it.
