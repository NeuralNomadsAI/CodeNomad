# Projects and tabs

Closing project tabs, temporary workspaces, the new-instance launcher and the Git-unavailable degraded mode.

## Agent conventions

- Selecting the current saved-server policy preserves the picker intent and its in-flight opening. A changed origin, TLS or SSH policy creates a new selection; the picker lifetime and workspace receipt own cancellation.
- The saved-server picker keys the entire Dialog/Portal lifetime by the validated profile. Replacing the server disposes its browser, pending work and ARIA title before the next dialog mounts. Same-policy reselection retains the current lifetime; cancellation followed by reselection starts a fresh one.

**Remote opening ownership boundaries**

`openRemoteProject` receives an opaque `WorkspaceCreationOwnership` through signal-scoped `createInstance.onCreation` before dispatch. Every untransferred exit runs its idempotent discard, including rejected or resolved-but-obsolete creation. Explicit commits retire older claims for the same UI key; passive observations enrich their current claim. Cleanup and failed-settlement restoration retain the exact request/API/attachment and current occurrence.

| Boundary | Owner | Stale or cancelled outcome |
| --- | --- | --- |
| `await backendRegistry.ensure` | Shared registry admission/client | Current-intent check ends the opening before creation; the registry retains its shared client. |
| `await retryWorkspaces` | Shared inventory flight and captured attachment | Current-intent check ends the opening before creation. |
| `await createInstance` / POST | Captured creation request, API and attachment | Abort and caller-finally share one cancellation flight. Definitive route rejection settles the request; uncertain outcomes retain the original responsibility until confirmed cancellation. |
| Response / commit wait | Exact receipt and prospective occurrence | Cancellation joins that same request; publication checks the attachment and commit gate. |
| Resolved create continuation | Exact committed occurrence and receipt | Caller-finally discards the captured claim. UI removal matches its current request key; retired cleanup preserves replacement occurrences. |
| Synchronous tab selection → release ACK | Guarded occurrence transfers to its tab; release retains the captured API/request key | Selection rechecks ownership and reports successful transfer. Subsequent intent changes preserve the adopted tab; release completes or retains its exact retryable claim. |
| Native selection reply | Correlated profile-selection ticket and exact opener | ACK, refusal or timeout consumes its matching ticket. Current browsers and adopted tabs follow their own ownership lifetimes. |

- Claim discard coalesces across abort, creation continuation and caller-finally. Failed bounded settlement keeps its original receipt; failed retired cleanup preserves the replacement's projection. A reused record stays available while only its new request is cancelled.

- Experimental multi-backend opening uses `remote-project-open.ts` and `remote-server-browser.tsx`: the host's saved policy is captured as an immutable selection, rechecked before admission and publication, then `backendRegistry.ensure` supplies the exact client to `createInstance`. Caller cancellation owns only that creation receipt. The main renderer selects an ordinary instance tab; its server icon and visible server name distinguish remote projects, including duplicate server labels. Browse, typed paths and remote recents share this flow. Clone and temporary actions retain their local home-page owner. Explicit Retry and successful authentication recover a retained inventory through `retryWorkspaces`; incompatible metadata and HTTP 426 refuse admission.

- Restore claim settlement uses the receipt's exact attachment/request key, including terminal events and delayed callbacks. A confirmed release, cancellation or stop drops the descriptor and its client/API/attachment references; explicit create-route rejection ends its receipt, while transport failures, aborted requests and uncertain server errors retain their captured responsibility. Settled requests keep primitive identity fences for duplicate responses, and cancelled occurrences keep lightweight event tombstones until an explicit user opening. Unsettled and revoked claims retain their full owner for settlement retries, independently of replacement occurrences.
- List and event ingestion consult the exact backend/attachment/request cancellation fence before publishing even the first descriptor. Cancellation intent and explicit user opening capture their logical order before dispatch; confirmed settlement applies that immutable cancellation order. Unconfirmed cancellation retains its unknown owner. Primitive order keeps delayed cancelled descriptors stale while preserving a later user occurrence, and a genuinely later cancellation takes precedence even when the earlier user response arrives last; reused observations retain their user ownership. Stop dispatch can settle an owner during its in-flight release, and delayed HTTP completion uses the settled slot identity.

- `createInstance` accepts an explicit backend client and otherwise uses the local backend. Remote admission requires the strict multi-backend flag, the registered client, its live attachment and its bound relay proof. Capture a memory-only operation receipt before POST or queued close: backend, exact client/API, attachment, physical directory and raw creation request id; response descriptors add raw workspace id and qualified UI key. List and SSE enrichment preserve that receipt. Creation callbacks, publication and failed-cleanup restoration recheck its attachment, while claim cancel/release retries retain the original API independently of caller cancellation. Refused settlement preserves its unknown claim and never selects a replacement client. Commit gates match request ids and physical paths within one backend; DELETE/release decode the UI key once at the HTTP adapter. Temporary and ordinary local entry points keep their local owner. Saved remote tabs remain preserved and remote startup creation remains skipped. Explicit failed-inventory recovery is a prerequisite for wiring remote consumers; `ensure` remains coalesced admission.
- Remote workspace inventory recovery is explicit through `backendRegistry.retryWorkspaces(profileId)`. It requires the admitted client and captured event attachment, revalidates fresh metadata/identity/relay authority before reading, and repairs availability only on current success. Concurrent demands share one flight; `{ invalidate: true }` requests at most one serialized follow-up. Failure retains the display snapshot and rejects the demand. Continued invalidation parks until a new demand. `ensure` retains its coalesced admission; consumers invoke recovery from an explicit Retry or successful connection action.
- Metadata validation and inventory availability retain distinct authority: a superseded live connection gate follows the latest metadata verdict; obsolete replies stay fenced. Inventory publication retains the attachment and metadata-failure epoch across healthy reconnects. Inventory failure stays unreachable through metadata-only success until explicit inventory recovery succeeds; an intervening metadata failure fences inventory success. Recovery and reconnect share the per-backend workspace-list reconciliation fence, retaining creation, cancellation and user-opening fences while the read is pending. The reconciler returns `false` for a superseded or skipped read; registry loaders propagate that outcome so only a current published inventory repairs availability.
- Host Git probes report `git_required` only for an absent executable (`ENOENT`). Timeouts, killed processes, unsuccessful exits and invalid version output yield `git_probe_unavailable` (503, retryable); the availability advisory propagates uncertainty to its best-effort caller rather than publishing installation guidance. The probe retains its five-second deadline and rechecks on demand.

- Closing a project tab detaches it immediately and requests deletion of that occurrence's logical backend workspace record; failures notify and never retry automatically. Separate occurrences of the same folder are independent. A `workspace.stopped` deletion closes the same record in other windows and notifies only windows displaying it that did not initiate the close. CodeNomad never evicts native Locations; OpenCode sessions keep running and reopening finds them. Whole-window close, app quit, renderer reload and backend shutdown keep existing restoration behavior. Temporary discard and server stop events use local-only tab detachment, not another DELETE; Keep closes the retained project normally.
- Git is a full-functionality prerequisite, with directory-only degraded conversations when the backend cannot find Git. Only the explicitly opened physical folder is session authority in that mode; never infer sibling worktrees from native project IDs. Keep ancestor/descendant mutation identities covered by the deletion fence across Git availability changes. Inform agents through the owned native `codenomad.git-availability` instruction before prompts/custom commands, remove stale context after recovery, and keep this advisory separate from fail-closed environment synchronization. Do not add a blocking Git setup UI. Validate with `scripts/test-git-degraded-native.mjs` using an isolated CLI/database and provider.
- Temporary instances (`workspaces/temporary-workspaces.ts`, UI `stores/temporary-instances.ts`) are ordinary non-Git workspaces on CodeNomad-created direct children of `<config>/temporary-workspaces`. Registry membership (`temporary-workspaces.json`), not location, makes a folder temporary; keeping only unregisters it and adds a named recent project. Discard deletes only registered children of that root, refuses running conversations and other open tabs of the folder, removes conversations deepest-first, closes the workspace before deleting the folder and keeps failed removals registered; such a folder is reachable only by browsing to it. Closing a temporary tab from the UI asks Keep/Discard/Cancel, except that an untouched one (no conversation, file or unsent draft) closes and is discarded silently (`onlyIfEmpty`: the server refuses with `temporary_has_conversations`/`temporary_not_empty`, and any failure of that quiet discard returns the choice without an error). Before the server stops it, a visible temporary tab yields to its neighbour (or closes if alone) and a refusal restores it in place; `workspace.stopped` likewise closes the tab first and clears the instance in a microtask, because clearing a visible shell's state in the same update as its tab freezes the window. Same-minute names get a `(n)` suffix. Registry changes broadcast `workspace.temporaryChanged`, which clears kept marks in every window. Open temporary tabs are saved and restored with the app state like any project tab (still marked temporary). Only the choice dialog overrides initial focus (to its last, non-destructive choice); confirms keep focus on Cancel. Refusals use stable `temporary_*` codes localized by the client. Validate with `scripts/test-temporary-workspaces-native.mjs` against an isolated CLI.
- The tab-bar new-instance button follows the last tab like a browser: the instance `TabScroll` frame only spans its tabs and the button sits after it, outside the scroller (so focusing it never scrolls the strip), ending up at the strip's end once tabs overflow. Dragged tabs stay visually within the tab list like a browser's (`KeepDraggedTabInStrip`), while the drop slot follows the pointer's unbounded position (`closestUnboundedCenter`). The button keeps its click (full home page, Cmd/Ctrl+N) while a long press, right-click, Alt+Down, Shift+F10 or Menu opens the anchored `NewInstanceLauncher` (`lib/long-press.ts`; only Escape returns focus to the button, never over another surface or the home page): search-first recent projects (an open project switches to its tab) and Browse/Temporary/Clone only. Remote servers, SideCar and management (rename/remove recents, servers, settings) stay on the home page. Browse/clone flows live once in `components/new-instance-dialogs.tsx` (with optional home-only add-server setup) and recent-folder display helpers in `lib/recent-folder-display.ts`, shared with `FolderSelectionView`; styles in `styles/components/new-instance-launcher.css`.
- The clone dialog (`components/new-instance-dialogs.tsx`) suggests the repository's `git clone` folder name (`lib/clone-destination.ts`) inside a parent: the folder chosen with Browse, else the server-scoped `ui` state `lastCloneParent` (the folder above the last successful clone), else the folder above the most recent project. A destination the user types is kept as entered and sent unchanged; the server creates it.
