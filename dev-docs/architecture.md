# CodeNomad Architecture

## Overview

CodeNomad is a SolidJS UI and Fastify server hosted by Electron or Tauri. The official `@opencode/client` dependency pins live in the [server](../packages/server/package.json) and [UI](../packages/ui/package.json) manifests; the runtime CLI is independently managed.

```text
Desktop host -> CodeNomad server -> one shared OpenCode service
                    ^    |
                    |    +-> CodeNomad /api/* and /api/events
                    +------ UI clients through /workspaces/:id/instance/api/*
```

CodeNomad's bundled native plugins (automation, see [BROWSER_AUTOMATION.md](BROWSER_AUTOMATION.md); session pruning; Missions) load through native V2 discovery; none owns the daemon.

## Shared Service And Locations

`packages/server/src/workspaces/opencode-service.ts` runs the selected host or WSL CLI's official `service status`, `service start`, and `service get password` lifecycle, validates the authenticated loopback endpoint, and pins that identity while active. It connects to one externally owned global daemon and never stops it on backend shutdown. An acquisition more than 30 seconds after the last check repeats discovery: a different discovered daemon (URL, PID, version or credentials) replaces the connection, while a discovery that fails or finds no service keeps it until the next interval. Failed location validation, proxy transport or authentication failures and upstream event-stream EOF/errors retire the connection.

OpenCode owns the daemon's standard state and database. Configured allowed environment variables and `NODE_EXTRA_CA_CERTS` apply only if CodeNomad starts a missing daemon; a running daemon keeps its environment. `OPENCODE_DB` and `XDG_STATE_HOME` never reach the daemon or session environments (`workspaces/host-opencode-service.ts`, `workspaces/session-environment.ts`). WSL support requires Windows localhost forwarding and executes the Linux CLI lifecycle inside the selected distribution without cross-namespace PID operations.

`packages/server/src/workspaces/manager.ts` treats selected folders as native OpenCode locations:

1. Validate the directory with `client.location.get`.
2. Store the returned `LocationRef` and publish the logical workspace.
3. Reuse the shared service for every additional directory.
4. Closing a project tab deletes that occurrence's logical workspace record (`DELETE /api/workspaces/:id`; see [PROJECTS.md](PROJECTS.md)).

## Native Profiles, Windows, And Client State

Electron POSIX startup discovers the shell environment in an isolated process group,
bounded to three seconds and 1 MiB. The framed emitter keeps a referenced three-second
exit timer so its leader stays signalable until group cleanup and expires if the
discovery parent disappears. Cleanup rejects signal errors other than `ESRCH`.

Electron and Tauri run one native singleton process and one CodeNomad backend per data profile/config pair ([DESKTOP_DATA_PROFILES.md](DESKTOP_DATA_PROFILES.md)), isolating singleton identity, backend/browser storage and client state. A second launch opens another UUID-backed window by default; Advanced settings can restore most-recent-window focus, while `--new-window` always creates another window.

`--connect-server <value>` (or `--connect-server=<value>`) asks for a remote window; both hosts parse it beside `--folder`/positional folders (Electron `startup.ts` `parseLaunchIntent`, Tauri `launch.rs`, Windows second-instance forwarding included) and keep the raw value (empty when missing). The host never resolves or connects: it queues the value to a local window (`window:connections-pending` / `desktop:connections-pending`, pulled and acknowledged in order like launch folders), and the renderer resolves it against the saved remote servers (`lib/launch-connect-target.ts`: id, then name, then an http(s) URL without user info or fragment) and runs the same `saveServer` flow as **Connect** (probe, TLS/certificate prompts, proxy session, `openRemoteServerWindow`). A connect-only launch (no folders, no `--new-window`) skips the startup window restore and, without an open local window, runs in a hidden, unpersisted launch window (`connectOnly`/`connect_only`) that the host closes once the remote window is open (`connect-launch.ts`, Tauri `local_windows.rs`). That window holds no slot of the 16-window limit (registration and new-window admission share one user-window count) and is never an MRU, focus or launch target, so folder launches arriving meanwhile open an ordinary window. Launch-owned hidden windows (the launch window and, on Electron, a remote window still loading for a launch) never count for the last-application-window decision (`isLaunchWindow`, Tauri `is_final_application_window`'s launch labels): closing the last visible window quits normally and keeps its saved state. The saved Preferences window is restored only by a normal start: a connect-only launch holds it (`DeferredRestore`, Tauri `startup_restore_deferred`) until its fallback. It never prompts or shows errors: a failure, a connection that needs a prompt (the Tauri local-certificate install, `InteractionRequiredError`), a backend error or a 60-second timeout makes the host perform the normal restore and queue the connection (with its failure, if any) and every one still pending to the restored window, which reports or runs them visibly; if that restore fails, the launch window itself is promoted and shown. Launch connections open the remote window with `requireLoad`: on Electron a failed first page load destroys the hidden new remote window and rejects instead of showing the loading screen (Tauri cannot observe the remote page's load result and shows the webview's own error page). A forwarded connect-only second launch runs in the most recent window instead of opening a new one. Electron forwards the second launch's own parsed intent through `requestSingleInstanceLock(additionalData)` (`forwardedLaunchData`/`readForwardedLaunchIntent`), because Chromium reorders the forwarded argv; the Windows Tauri single-instance plugin forwards arguments joined and split on `|`, so every Windows Tauri launch refuses an argument containing `|` with a startup error before the plugin runs (`launch::pipe_argument_error`), which keeps forwarded argument boundaries exact.

Remote windows are never restored, and the user can always reach a working local window. Rules (both hosts):

- Every new local window signs itself in to the local server: Tauri gives each one the session cookie before its first backend navigation (`LocalCliAccess::session_cookie_for`, read through `ready_local_access` without the lifecycle lock), because WebView2 drops a session cookie once every window of its store has closed (the last local window closed beside a remote window, or a launch connection). Electron keeps the cookie in the application-lifetime default session.
- Closing the last local window keeps its saved state even while remote windows stay open, as quitting would (Electron `MultiwindowLifecycle.hasOtherLocalWindow`, Tauri `LocalWindows::has_other_user_window`); the next local window (File → New Window, a later launch or the next start) reopens it. Only a local window closing beside another local window forgets its state.
- A local window showing a page that does not run the application (loading, sign-in, pairing, `/auth/*`) closes and lets CodeNomad quit without waiting for a client-state flush it could never answer (Electron `isListenerlessDocument` in `renderer-client-state-flush.ts`, Tauri `awaits_renderer_flush` over `is_listenerless_document`).
- A remote window whose server cannot be loaded keeps a way back. Electron loads its own loading page with `#remote-unavailable=<token>` (`lib/native/remote-unavailable.ts`): **Try again**, **Open a local window** and **Close window** (`remote:retry`, `remote:openLocalWindow`). `RemoteRecoveryPages` and `showRemoteUnavailable` (`electron/main/remote-recovery.ts`) load a new document for every token (a `recovery` load counter in the query, so a Try again whose load commits nothing, such as HTTP 204, still replaces the page) and authorise a request only from the registered remote window's main frame with that token and the origin bound once by that load's own commit. Any later main-frame commit or a renderer crash revokes the token for good. The window remembers its revoked recovery documents (up to 16), so when the user brings one back (native Reload, also after a crash, or history) its commit shows a fresh document with a fresh token; a crash itself never reloads. A URL the page can rewrite (History API) is never the authority; `remote-recovery.test.ts` checks this through real Electron IPC. Tauri remote windows show WebView2's error page with its reload button, their native title bar and File menu.

OpenCode sessions and messages are shared through the global daemon. Window membership, tabs, drafts, view state, and native bounds are local to each UUID window. Client-state V3 is a per-window envelope over the V2 SHA-256 content-addressed partition graph: immutable partitions are prepared before atomic root publication, writes and migrations are fenced by current ownership and renderer authority, and garbage collection runs after publication while retaining every partition referenced by any window.

Electron and Tauri local windows load credential-free HTTP(S) preview pages directly in hardened native child views: Chromium, WebView2 (Windows), WKWebView (macOS 14+) or WebKitGTK (Linux). Cookies and localStorage persist in one preview store per profile/configuration, separate from the trusted app renderer and remote windows. Documents and native navigation histories remain session-owned. Tauri's shared `embedded_view.rs` layer owns creation, storage, geometry, visibility, overlay masking and mandatory navigation/permission/download/new-window guards; `browser_controller.rs` retains session registrations and browser behavior. Primary `local-*` webviews alone receive application capabilities. Native preview element comments are unavailable. Agent browser automation supports Electron and Tauri Windows/macOS/Linux. WebKit presets fit CSS viewports and apply mobile identity, with native density and input limits described in [Device profiles](BROWSER_DEVICE_EMULATION.md). See [Native Hosts](BROWSER_AUTOMATION.md#native-hosts) for the common contract and remote-project-tab adoption.

Plain-browser and remote-view previews use unguessable capabilities for HTTP and WebSocket proxy traffic. Preview proxies never forward request cookies and strip the target's `Set-Cookie`. Path-proxied preview responses (`/previews/<token>/…` and the Referer asset fallback, every content type) carry `Content-Security-Policy: sandbox` with the iframe's flags (`previews/sandbox.ts`, shared with the UI) and `Referrer-Policy: same-origin`, so a preview document stays opaque even when opened outside its iframe and its capability path stays out of Referer headers to other sites. The per-token `preview.localhost` host has its own origin and receives neither override. The proxy rewrites root-relative URLs in HTML attributes, CSS `url()` and JavaScript imports, and the runtime bridge rewrites fetch, XHR, WebSocket, EventSource, history, untargeted link-click and form-submission URLs, and gives opaque documents whose storage access throws one stable in-memory `localStorage`/`sessionStorage`/`document.cookie` object each for the current page load, detected by reading alone so working storage (the per-token host opened on its own) stays native. Other root-relative requests (a CSS `@import` string, for example) reach the static UI or dev-proxy handlers, which proxy them to the preview named by their Referer when the request has a CodeNomad session, as every direct-listener request has with authentication disabled; stylesheet subresources send the stylesheet's URL as Referer even from an opaque document. Remote Control refuses this fallback while previews are off. Browser preview iframes are opaque-origin sandboxes without `allow-same-origin`; preview element comments use a source-checked message bridge instead of parent DOM access. SideCar iframes add `allow-same-origin` by design: a SideCar is a trusted extension of CodeNomad, and its scripts run with the application's origin and access. `/sidecars/*` authenticates with the `SameSite=Lax` session cookie and rejects `Origin: null`, which an opaque frame cannot satisfy.

## API Boundaries

CodeNomad control APIs live under `/api/*`. Important routes include:

- `/api/workspaces` and `/api/workspaces/:id/worktrees/*`
- `/api/workspaces/:id/worktrees/:slug/git-status|git-diff|git-stage|git-unstage|git-commit`
- `/api/events` and `/api/client-connections/pong`
- `/api/storage`, `/api/settings`, `/api/filesystem`, `/api/speech`
- `/api/opencode-plugin/automation`, authenticated by a per-process loopback token and restricted to CodeNomad-owned locations
- `/api/remote-control/*`, managed from the host only; `POST /api/remote-control/pair` and `/remote-pair` answer only through Remote Control ([REMOTE_CONTROL.md](REMOTE_CONTROL.md))

Authentication and Remote Control admission judge `routedPath()` (`server/routed-path.ts`), the path Fastify's router matches (`/%61pi/x` routes as `/api/x`), and refuse targets it would reinterpret. Never base an access decision on the raw request target.

Native OpenCode requests use `/workspaces/:id/instance/api/*`. The Fastify proxy exposes an explicit method/path allowlist, adds shared-service authorization, validates prompt files, defaults safe requests to the workspace location, and rejects locations/directories outside the selected workspace or its worktrees. Session routes also verify `session.location.directory`. Never trust a browser-supplied worktree path: resolve ownership server-side. Upstream additions are exposed only after an explicit proxy review.

Yolo state endpoints live at `/workspaces/:id/yolo/sessions/:sessionId`; Yolo notifications use `/api/events`.

## Client And Events

`packages/ui/src/lib/sdk-manager.ts` uses `OpenCode.make()` and caches generated Promise clients by instance proxy path. `packages/ui/src/stores/opencode-client.ts` is the root-client authority; native directory/location fields select the worktree.

The server holds one `client.event.subscribe()` stream. `InstanceEventBridge` maps native location events to CodeNomad `instance.event` records, and `/api/events` multiplexes them with workspace and Yolo events for the browser; heartbeats use `POST /api/client-connections/pong`. The stream is volatile and has no replay guarantee: reconnect must reconcile sessions and pending requests and reread authoritative file/config state. Pending recovery uses the loaded-only broker, never worktree-wide ordinary lists; see [compatibility](OPENCODE_COMPATIBILITY.md), whose Agent conventions also specify relay ordering and ownership fences.

### Per-backend transport

Remote clients resolve CodeNomad HTTP routes, panel-extension routes, deferred tool images, the default events URL and workspace SDK proxies from the backend origin through `BackendTransport.url()` / `resolveBackendUrl()`. A trailing slash on the base URL is optional; a path prefix on that base is discarded for these root-relative routes. An explicit absolute events URL is preserved. The SDK manager and panel-extension factory take the backend's `url` and `fetch`; `toolImageSource` takes a backend's `url` or an explicit HTTP(S) base.

Injected local bases preserve their resource-specific joining contracts through the shared resolver: HTTP/auth use URL resolution, panel extensions and SSE append their paths verbatim, and deferred images and SDK proxies trim trailing base slashes before appending. `buildInstanceBaseUrl()` exposes the injected-local SDK joining contract. The `append` and `append-trimmed` resolver modes serve these local adapters; remote factories use the backend's URL resolver. Storage, metadata and Mission requests delegate URL construction to the same backend API; event transport delegates to its API's already resolved events URL, adding connection identity query parameters there.

`packages/ui/src/lib/backend-client.ts` describes one CodeNomad backend as a `BackendClient`: base URL, events URL, authenticated `fetch`, login recovery (`auth`), `api` (`createServerApi`), `events` (`ServerEvents`), `storage`, `meta` and the OpenCode `sdk` manager, each built by its module's factory. `createBackendClient()` builds another backend's client from an absolute http(s) base URL (anything else throws a `TypeError`); its events stream connects only on `events.start()`, its `api`, `storage`, `meta` and `sdk` requests all go through its own `fetch`, its 401s probe only its own login, and a restored login restarts only its own stream. `localBackend` is assembled from the module singletons (`serverApi`, `serverEvents`, `authRecovery`, `authenticatedFetch`, `storage`, `sdkManager`, `getServerMeta`), which remain the same mutable objects their importers and tests use; the `serverEvents` singleton connects at import. `backends` starts with `local`; the saved-profile registry owns remote publication through `registerBackendClient()`. `backendOf(instanceId)` returns the registered owner of the instance key's backend and throws for an unregistered one. `lib/backend-transport.ts` is the only reader of the injected API base and events URL (through `lib/api-base.ts`); `EventSource` and `fetch` are resolved per call. Network code takes a backend's transport (`BackendHttp`) with the local one as default, never the injected globals.

### Saved-profile backend relay

`createRemoteBackendClient(profileId)` constructs an unregistered client whose resolver prefixes HTTP, auth, SSE, SDK and media routes with `/api/backends/<profileId>` on the local CodeNomad origin. Electron, Tauri and local browsers use the same server-side transport. The host-owned `config.ui.settings.multiBackend` flag defaults to false and accepts only boolean true. Its configuration has no visible control. While off, the local registry and existing tabs retain their behavior; registry demand performs zero remote IO.

`stores/remote-backends.ts` owns the renderer's `backendRegistry`, implemented by `stores/backend-registry.ts`. `ensure(profileId)` rereads host policy and saved profiles, coalesces a candidate per profile and reads authenticated metadata afresh through the relay with `no-store` and an eight-second deadline, independently of display caches. Compatible metadata precedes client registration, event fan-in attachment, SSE start and the backend-owned workspace list. Profile ids remain backend ids. Reactive states are idle, admitting, compatible, refused, unauthorized and unreachable. Merely observing profiles starts no network work.

Renaming a saved profile retains its client. Address/TLS change, removal, explicit detach, disposal or flag off revoke fan-in authority first, abort candidate IO, dispose stream/retry/watchdog resources and remove the client. Late candidate replies check both their exact entry and current saved policy. A fresh attachment has a new signal. Temporary stream failure preserves the attachment and existing tabs, using ordinary retries. Each remote connection attempt rereads metadata before acquiring EventSource or delivering open/domain resyncs; contract or server identity changes refuse and revoke the backend. Superseded connection attempts abort their validation reads. Workspace-list failures retain the admitted client and expose unreachable until recovery.

`server/routes/backend-relay.ts` relays `/api/*` and `/workspaces/*` through `codenomad-servers/browse-manager.ts`. The manager resolves the saved `state.ui.remoteServers` profile and owns its client, TLS policy and private credential store. `opencode/servers/transport.ts` validates and pins each DNS answer for the dial, verifies TLS against the saved hostname, refuses redirects, strips caller credentials and browser metadata, and adds only the backend-held identity. Remote mutations use the explicit device protocol described in [REMOTE_CONTROL.md](REMOTE_CONTROL.md#saved-profile-relay). Login and logout at the relay operate on the backend's saved identity. Host-only remote routes and nested relays remain inaccessible.

`index.ts` owns one `RemoteServerBrowseManager`, its settings-change subscription and shutdown across HTTP, HTTPS and the private bridge listener. Standalone listener managers sharing the backend's `SettingsService` retain the same connection state: credentials, clients, pending connections, queues and profile authorities. Closing one owner releases its lease; the last owner closes the shared connections. Forget revokes the shared authority immediately, across every listener.

Connection and browse admission captures an immutable profile authority before queueing: profile id, normalized origin, TLS policy and an object-identity generation. Dispatch and credential publication check that captured generation and the current saved profile. Address/TLS changes and removal revoke queued work as well as active connections; queued passwords remain bound to their admitted destination. The private store binds each identity to both origin and TLS policy. An entry without a TLS-policy field binds to verified TLS.

Registry-created remote candidates opt into `bindRelayAuthority`. Fresh metadata reads return `X-CodeNomad-Backend-Authority`, minted locally from the captured profile authority as 32 random bytes in memory. The bounded metadata read observes `serverId` and rechecks that exact authority before publication; upstream homonymous headers and body fields cannot supply the local header. The registry validates compatibility and candidate ownership before admitting one immutable proof to that client's transport. Reconnect confirms the same proof and remote identity. A different observed identity revokes the authority; replacement behind the same origin remains undetected until an identity observation.

Each opted-in fetch sends the proof, including cancel/release/close without attachment signals. Resource URLs and EventSource carry the same value in `__codenomad_authority`; SDK proxy bases stay plain and their fetch carries the header. The local relay removes both carriers before upstream dispatch. Unknown, malformed, conflicting or revoked proofs fail before client construction, fetch or DNS; missing proof in the opted-in transport fails before HTTP dispatch. Bootstrap permits only exact GET metadata, GET auth status and POST login, so a candidate can authenticate before admission. Bound login/logout also validate the existing proof. Retarget, TLS change, removal/recreation, Forget, explicit principal replacement and last-owner shutdown revoke the generation; rename and same-principal cookie renewal preserve it. Existing non-opted-in clients and the local backend retain their request contracts.

A revoked cleanup retains its original client and can remain pending when refused. Retry never recaptures a replacement authority. Already dispatched mutations may settle remotely, with no replay or rollback guarantee from revocation. The proof adds a destination-generation fence within the existing local-origin, authentication, route and TLS guards.

| Boundary | Admission and revocable authority |
|---|---|
| Local relay and browse/connect/forget | `guardLocalBackendCaller`: local non-ingress socket plus exact loopback self Origin; same-origin GET/HEAD may instead carry a loopback self Referer and `Sec-Fetch-Site: same-origin`. Trusted same-origin SideCars share this authority. |
| Saved remote client | Backend-shared authority captured at admission; exact saved origin and confirmed TLS policy; credentials in `remote-server-credentials.json` beside the config with mode 0600. Each client owns an AbortController; request cancellation composes with it through uploads and streamed response bodies. |
| Profile changes and removal | Synchronous `storage.stateChanged` reconciliation revokes the generation, closes changed/removed clients and pending connections, deletes credentials, and fences queued dispatch and pending authentication before persistence. Forget revokes every listener; backend shutdown closes their shared owner. |
| Remote device | The remote gate authenticates the private device credential on each request, admits the reviewed method/path catalog, marks device scope on both listeners, and retains sockets for revocation, eviction, Stop and shutdown. Browser pairing judges ingress-socket membership; browser Origin admission retains its own policy. |
| Response publication | Selected safe response headers, private-cookie removal, `no-store`, sandbox CSP and `nosniff`; decoded transfer lengths follow decoded bytes. Local caller disconnect closes the upstream transfer. |

The UI boundary registry below classifies relay construction and URL resolution as retained-client operations; existing A/P callers supply the same cancellation signals through this transport. A sent mutation can settle remotely while its revoked caller loses publication authority.

### Server metadata contract

`GET /api/meta` adds the public `serverId` UUID, `apiContract` integer and `capabilities: string[]` to the shared `ServerMeta` response. `SettingsService.getServerId()` reads `server.serverId` authoritatively from the selected config YAML. When absent, it creates `<config-target>.server-id` exclusively with `openSync(..., "wx", 0o600)`, writes a UUID, then rereads the config and persists the winning UUID. Concurrent initializers read the same immutable claim; config symlink aliases share the final target's claim. Readers retry an incomplete UUID for at most one second while its creator finishes writing. Each distinct fresh config receives its own UUID; copying a config preserves its identity.

A complete claim survives a crash or failed YAML write and supplies the same UUID on retry. An incomplete or invalid claim remains untouched and requires explicit operator repair: stop all servers using this config and restore the known UUID, or explicitly remove an incomplete claim only after confirming that no stable identity was advertised. Identity initialization preserves other owners and server settings. Unreadable, read-only or malformed config, invalid stored UUIDs/claims, conflicts and persistence errors log a warning; startup continues with `serverId` omitted from metadata and remote registry admission refused. An existing valid YAML identity is authoritative and supports read-only startup without a write.

`packages/server/src/meta-contract.ts` defines the CodeNomad contract, initially **1**. Increment it whenever an existing UI-consumed CodeNomad wire contract breaks; additive optional fields and capabilities preserve the integer. Review the server and UI consumers together. OpenCode compatibility follows the consumed native API/capability contracts described in `OPENCODE_COMPATIBILITY.md`.

Initial capabilities identify implemented CodeNomad route families: `workspaces` (`/api/workspaces` inventory and lifecycle), `workspace-files` (workspace filesystem routes), `workspace-git` (workspace Git reads and mutations), and `events` (`/api/events`). Each route retains its own authorization, ownership and runtime availability checks. Optional features may add distinct capability names; unknown names can be ignored.

`BackendClient.meta.getServerMeta()` retains these fields in its existing per-client snapshot and signal-owned project cache. The wire fields are optional for older servers and an unavailable stable identity. The pure `backendCompatibility()` policy returns `compatible` for exact equality with the local CodeNomad contract and a nonblank `serverId`, and `refused` otherwise. Registry admission reads fresh metadata directly. Refused profiles remain saved for an explicit retry after updating the server. Never open a webview or separate window for a refused backend.

### Per-backend event fan-in

Attachment removal aborts authority before reactive disappearance is published. Reactive publication and each unsubscribe have independent failure boundaries, so removal notifications and the remaining cleanup still run. Mounted preference readers resolve absent/revoked server buckets to empty data with host presentation/model inheritance; load and mutation admission requires the captured live owner. Remote preference edits serialize by `state/ui` or `config/ui`, deriving list changes at their turn after loading and the preceding edit's publication; explicit Mission expectations retain their CAS checks. Storage owner caches and read flights belong to the exact attachment signal: reusing the same client starts fresh flights and fences revoked reads and ACKs before cache publication or subscription delivery. Flight cleanup releases only its recorded request; sent mutations retain their durable server-side result. The local preference owner keeps its existing write ordering. Asynchronous remote default-model selection waits for its preference owner before reading recents.

`ServerEvents` owns one backend's EventSource, auth probe, pong, staleness watchdog, retry timer and connection generation. The synchronous `backendEvents` singleton lives in `lib/backend-events.ts`; importing this module or `captureBackendOperation` constructs only the fan-in. `lib/server-events.ts` re-exports the same singleton, connects the local source and attaches it. The fan-in scopes CodeNomad envelope instance/workspace ids (including descriptors and log entries), adds `backendId` for another backend and preserves native event/location data, generations and physical paths. Local events retain their object and ids, and `serverEvents === localBackend.events` stays the local source. Lifecycle callbacks carry the source backend (`onOpen(backendId)`, `onTransportStatus(status, backendId)`); `forInstance()` filters against a view's current instance. Each backend has its own SSE manager and transport display state, with the existing session hooks receiving globally scoped instance keys. Reconnect refreshes, display invalidations and foreground recovery target only that backend.

`backendEvents.signal(backendId)` and reactive `signalForInstance(instanceId)` expose the attachment's AbortSignal; an absent instance attachment yields an aborted signal. `captureBackendOperation(instanceId, parent?, owns?)` captures that authority, combines the optional parent signal and exposes `signal` and `current()`. Attachment-owned work retains this token across awaits, callbacks, queues and timers, combining it with client, view and request-generation predicates before publication or follow-up work. Reattachment creates a distinct authority even when the backend id and source object are reused. Notification recipients are captured before delivery, and each delivery checks the same authority again. The inventory below distinguishes attachment-owned work, durable client operations and caller/view-only guards.

Detaching a source unsubscribes its fan-in and aborts its attachment authority. A final disconnected status is delivered while the id remains absent; `onDetach(backendId, revokedSignal)` always identifies the removed owner, and cleanup checks that token before releasing keyed state. Removal disposes and deletes the backend's SSE manager, reactive connection records and foreground recovery controller, clears its integration connection epoch and binding authority, and permits a fresh owner on reattachment, including from inside a callback. Status reads observe existing managers without creating owners. Disposing `ServerEvents` also detaches every attached fan-in, fences pending connection acquisition and callbacks, closes its captured transport, clears reconnect/watchdog timers and browser/auth subscriptions, aborts event-owned auth probes and pong IO/backoff, and releases source subscriber sets. Connection acquisition, reconnect scheduling and notifications recheck disposal and connection generation at callback boundaries.

Foreground recovery passes its signal through session/message reads, pending-request invalidation, worktree reads and inbox follow-ups; its continuations check revocation before further reads, invalidations or message reloads. Workspace-list reconciliation captures its attachment and list-request authority. Worktree reads coalesce by signal/client owner, with request-identity cleanup. Authentication probes coalesce within their request owner's signal, inherit the originating request's cancellation even on a pong 401, and publish while both their login generation and accepted-observation order remain current. Each backend client owns its storage, metadata and SDK caches; workspace snapshots and view demands follow their instance/view lifetime and workspace-stop cleanup. Other event consumers and their concrete request/coalescence boundaries are inventoried below. The local source remains attached for the page lifetime.

Storage retains dispatched owner writes per client/document across attachments. A replacement's first owner load, strict revalidation and direct writes wait for those requests to settle, then loading reads the durable document afresh before preference edits compose their patches. Config and conditional Mission writes share a document barrier; other documents and clients remain independent. Each wait uses the ten-second owner reconciliation budget and fails closed on expiry, retaining the sent request and barrier through settlement for explicit reload. The shared renderer applies this ordering in Electron and Tauri while the local owner's request layout and ordering stay unchanged.

### Backend instance identity

Composer history keys preserve the exact physical directory for the local backend and prefix it with the backend id for another backend; `PromptInput` passes that persistence identity separately to its state hook. Mission completion seeding uses the project scope; pending-recovery notice deduplication uses the backend plus normalized folder. Instance/session-keyed drafts, attachments and caches retain their opaque instance keys.

Missions view scopes identify persisted presentation state only. `MissionControl`, the recurrence list and `MissionReader` acquire request directories from the owning instance's physical `folder`; archived passage readers capture that physical folder for their response guard independently of the view-scope cache identity. Preview scopes and history keys likewise remain persistence identities, while file and Location operations use physical directories.

`lib/backend-identity.ts` names instances and projects per backend. An instance key is the workspace id for the local backend and `${backendId}~${workspaceId}` for another one (backend ids match `[A-Za-z0-9_-]{1,64}`; never `:`, which instance-keyed maps split on); `Instance.backendId` is absent for the local backend. A project is one folder of one backend: `workspaceIdentity(folder, backendId)` matches saved tabs to live workspaces, occurrences, lifecycle events, project renames and temporary marks, and `projectScope()` keys Missions and preview view state (the folder itself for the local backend). `refreshWorkspaceList(backendId)` reconciles only that backend's instances under its own `BackendWorkspaceListReconciliationFence` entry, so one backend's list never closes another backend's tabs. Saved workspace tabs carry `backendId` only for another backend; restoration never creates such a tab on the local backend and keeps its state until its backend lists the workspace.

Native events include session lifecycle/output events (`session.created`, `session.renamed`, `session.moved`, `session.execution.*`, `session.retry.scheduled`, `session.step.*`, `session.compaction.*`, `session.text.*`, `session.reasoning.*`, `session.tool.*`), background Shell refresh via `shell.created`, `shell.exited`, `shell.deleted`, file invalidation via `filesystem.changed`, and configuration invalidation via `config.updated`. Each busy period settles with exactly one `session.execution.succeeded`/`failed`/`interrupted`; derive session activity from these events, never from the declared but unpublished `session.status`/`session.idle`.

### UI asynchronous backend inventory

Paths below are relative to `packages/ui/src` and cover files with detected backend accesses or backend-reaching continuations. Families include the initiating handler, delegated store/adapter, queued work and pagination. HTTP ownership follows the backend transport even when the feature also invokes native desktop methods.

- **A — attachment operation:** `captureBackendOperation` or a captured `signalForInstance` plus the row's local predicates. Follow delegated calls to their owner; admission and publication guards may live in different modules. The transport-method table identifies which HTTP methods accept cancellation: an A publication guard can coexist with a client-lived outbound request.
- **C — durable client:** intentionally retained backend client/transport for persistence, sent mutations, authentication/probing, resource cleanup or local-server bootstrap/administration. A dispatched mutation can finish server-side; any view continuation has its own predicate. Client caches and persistence queues survive SSE reconnection.
- **P — propagated:** callback, queue or transport receives its owner's signal/current predicate. Its caller supplies attachment authority; optional signals also admit client-lived requests.
- **V — view/request scope:** browser resources, dialog outcomes and retained presentation demand use their view controller/generation/identity. Backend runtime work delegated from these views uses its A or P owner; durable local services retain C.
- **DOM / IPC / EXTERNAL / COMPUTE:** rendering/device/browser work, native desktop-only operations, declared third-party HTTP and local calculation/storage encoding follow their component, resource, native request or external-site lifetime. Their helpers, timers and local names remain outside the table; mixed backend files name these local families alongside their backend work.

Generic **P** helpers inherit their injected read/action callback's authority, including helpers with no statically resolved IO. Queues, retries, debounce, trailing refresh, pagination, body/stream transfer and projection retain the caller's signal/current predicate, logical deadline and request identity across every dispatch, await and publication. Cancellation releases queued work and owned timers; coalescence joins compatible signal/client/request owners, and cleanup releases only its recorded lane. Retained view demand and stale snapshots can acquire a fresh operation after revocation. Dialog and menu dispatch retain the selected request/action and view lifetime; the supplied backend action owns admission and any sent mutation.

Generic **C** helpers retain the admitted client and creation/mutation request or receipt through persisted writes, serialized native startup-state transactions, abandoned-resource cleanup and retries. A dispatched mutation settles once under that owner; further reads, navigation and UI publication use the original operation's current predicate. Pure encoding, loaders and cache helpers inherit their caller's storage/native owner. Browser media and preview resources retain their element/source or capability identity and view cleanup.

**Demand V and operation A are distinct.** A displayed view, subscription count, cached snapshot, selected session or persisted preference may survive an attachment. Revocation ends its current A, while a subsequent attachment admits a new A for the still-retained V. The coalescence owner is the captured signal/client/request tuple; backend families identify their concrete lanes and cleanup.

Transient read, search and mutation indicators belong to the exact admitted operation and settle independently of its right to publish a response. Cleanup checks the recorded request, controller or exclusive local owner before releasing a flag; a replacement operation keeps its own busy state. Rebinding releases an abandoned cache flight without starting IO, and applies its new ownership before invoking abort callbacks. Exact schedule receipts similarly settle their dispatched intent while further reads, navigation and view callbacks require a current attachment/view.

A logical read budget retains one deadline and signal across slices, continuation, invalidation and shared demand; composing attachment cancellation preserves that logical identity. A replacement attachment acquires an independent budget. Restoration passes the caller's logical signal through SDK reads and keeps composed attachment cancellation private to queueing and settlement. Extension-host deadlines cancel their IO while the still-live attachment retains authority to answer its own deadline error; attachment/session revocation suppresses the reply.

#### Transport method families and IO authority

Session and chat consumers resolve `backendOf(instanceId)` from the global instance key. Missing owners fail at admission. Root and attached OpenCode clients use that owner's SDK cache; the root proxy path and CodeNomad conversation, history, pruning, goal, pending-request and permission/Yolo routes strip the backend prefix only at the HTTP boundary. Native session/message, prompt, interruption, compact and revert operations share this SDK transport. Existing A/P attachment and request authority fences queue dispatch, continuation and publication; dispatched C mutations retain their selected client. Instance teardown clears the owning registered SDK cache; an absent owner permits local view cleanup. The registered production backend is local.

Files and Git consumers resolve the same owner for tree listings (which register backend-side watches), mention listing/search, file reads/writes and image previews, Git status/diffs/history/branches/init/stage/unstage/commit, and worktree inventory/create/delete/session moves. These API methods strip the instance prefix at their HTTP boundary; paths and directories remain physical backend paths. Tree/history/diff lanes retain their attachment and controller authority; worktree lanes coalesce by attachment/client and clean up by request identity. Mention snapshot reads join only the same attachment and release only their recorded request. `workspace-open.ts` checks the instance backend before either Electron or Tauri IPC; tree, worktree and command controls use that same local-only predicate. Native folder selection and folder drop create local projects through the local launcher; device attachments transfer bytes. Never pass a remote instance or its paths to local native filesystem, editor or workspace-target actions.

Missions consumers resolve `backendOf(instanceId)` for panel/task/body/report/briefing reads, admission and lifecycle/cleanup mutations, schedule creation/settings/controls, recurrence and current/archived passages. Playbooks use the project's backend API; native profiles and Wayfinder Forms use its root SDK proxy. HTTP routes strip the instance prefix at the boundary, while persistence scopes and physical directories keep their distinct identities. Attachment authority fences every continuation and publication; in-flight reads join only their own generation and release only their own busy lane. The production registry starts with the local backend and admits saved profiles only behind the host's `multiBackend` flag.

Plugin controls/sources, integration catalog/bindings/host actions, skills and MCP use the project's owning backend API or root SDK. Global instance keys remain cache/view identities; only HTTP boundaries unwrap the raw workspace id, with physical directories preserved. `panel-extensions-backend.ts` binds inventory, catalog/package administration and contextual panel channels to that same owner: inventory is backend-global, while HTML becomes local sandboxed `srcdoc`. Attachment/request generations own coalesced reads, mutation indicators and prefill deduplication; cleanup releases only its captured record, and admitted mutations run once with guarded presentation/readback.

Provider subscription usage, Stats owner/cache/aggregation and account policy reads/writes resolve the project's backend and pass raw workspace IDs at the API boundary. Native credential catalogs and mutations retain the project's SDK client and exact directory. Attachment/source generations own display publication, repeated native status generations coalesce, and detached owners clear their presentation. Stats persistence remains in its backend's `state.ui.serviceUsage`; host preferences retain their existing scope.

`preferencesForBackend(backendId)` and `preferencesOf(instanceId)` select a settings owner; `useConfig(instanceIdAccessor)` follows a mounted project. Language, appearance, hotkeys, transcript presentation, notification routing, native window behavior and the server list share the host's local storage. Server configuration, recent folders, clone parent, binary history and instance data use the selected backend storage; instance storage keys carry raw workspace IDs. Model visibility, Mission defaults/library and model state inherit host values only when their server field is absent; explicit empty values remain server overrides. Each server owns its queues, pending intents, failures and storage subscriptions. Native Preferences carries only local project context; server and binary administration requires that backend's local host. The production registry contains the local backend and the settings target API preserves the persisted owner/key layout.

Session previews retain the project's backend client for create/delete and superseded-token cleanup, with attachment and navigation generations fencing publication and restoration coalescence. Frame and proxy paths resolve against that owner's origin; local URLs preserve the injected-local contract. Host-native browser-open requests discover only local instances and revalidate attachment, instance and session ownership after claim and creation. Project preview metadata and availability follow that backend. Settings → Info (`components/settings/info-settings-section.tsx`), releases, desktop updates, host version, SideCars and notifications keep their host owner. Remote tool/Markdown/attachment media use an authenticated owning-backend fetch and a mounted blob URL, revoked on replacement, disposal or attachment loss; credential-free external images stay outside that authenticated transport. Authentication identifiers never enter resource URLs or DOM attributes. Local media source strings retain their exact joining behavior.

Remote media blobs admit only PNG, JPEG, GIF, WebP, AVIF, BMP and ICO bytes verified by `lib/passive-image.ts` signatures and published with a canonical passive image MIME type. Inline data images pass through plain, credential-omitting fetch and the same admission gate; externally supplied blob references stay unavailable. SVG, HTML, unknown formats and non-image attachments use the existing unavailable state; never publish an openable resource for them. Refusal keeps active remote documents outside the UI origin. Remote blob images also suppress document-opening gestures, links, dragging and context menus; byte validation remains the security boundary when a URL is opened directly. Local sources and their server response CSP retain their existing contract.

`createServerApi` methods below retain their `BackendHttp`. **S** passes the supplied signal into HTTP/queued work; **scope** also carries `current()`/deadline for each transfer; **C** uses that captured client's request lifetime. **S+C** accepts request cancellation while retaining the admitted mutation's durable server-side outcome. Feature rows above separately specify admission/publication authority. Native SDK methods pass caller request options through `createInstanceFetch`, which composes any active attachment signal with Request/init cancellation. A dispatched mutation can commit server-side; durable receipts/resource cleanup retain client/request ownership, while runtime projection and rereads check the captured A.

## Persistence

CodeNomad configuration resolves through `packages/server/src/config/location.ts`: `config.yaml`, `state.yaml`, `remote-control-devices.json`, and `instances/` under `~/.config/codenomad/`. `config.json` is read only as migration input.

Backend shutdown closes SSE and upgraded sockets in Fastify's `preClose` hook and drains accepted local HTTP handlers before releasing workspace and native-parent authority. Completing responses close their keep-alive connection, including streams whose headers preceded shutdown, through a shutdown-only response-finish idle sweep. Permission recovery reads are cancelled; queued receipt writes, dispatched Yolo replies and Yolo persistence settle before workspace cleanup. Plugin leases and workspace cleanup run concurrently, and the success handshake follows resource cleanup. Native-parent responses remain readable through this drain. Mission mutations persist through their native RPC handlers in the shared OpenCode service.

Tauri revokes backend-generation capabilities before requesting shutdown. Its stdout and stderr readers retain their pipes until EOF, recording ordinary output with the launch generation while filtering bootstrap tokens and native-request frames. Revoked generations cannot publish readiness, navigate or dispatch native requests. Confirmed shutdown requires process containment and successful completion of both readers within the same absolute stop deadline (32 seconds on Unix, four seconds on Windows, clipped by the shutdown coordinator's deadline). Reader errors, panics and missing EOF retain ownership for retry and fail shutdown. Server COMPLETE/INCOMPLETE lines remain native diagnostics; process containment and stream completion are tracked separately from the server's functional cleanup status.

## Implementation Map

Server entrypoints are `packages/server/src/index.ts` and `server/http-server.ts`; shared-service authority lives in `workspaces/opencode-service.ts` and `workspaces/manager.ts`, event routing in `workspaces/instance-events.ts`, and bundled automation provisioning in `opencode/automation-plugin.ts`. UI native calls use `stores/opencode-client.ts`, `session-api.ts` and `session-actions.ts`; CodeNomad routes use `lib/api-client.ts`. Current integration conventions are in [AGENTS.md](../AGENTS.md) and the area documents it indexes.

## Agent conventions

- SideCar proxy cookies use `sidecars/proxy-cookies.ts`: authenticate locally first, then remove the actual auth cookie, the `codenomad_session` desktop namespace and paired-device cookie upstream; filter the same names from HTTP and WebSocket response cookies, preserving service cookies. Handshakes go through Node's bounded HTTP parser in `server/proxy-websocket.ts`, including non-101 responses and coalesced binary data. Same-origin SideCar scripts keep full application access: SideCars are trusted extensions by design.
