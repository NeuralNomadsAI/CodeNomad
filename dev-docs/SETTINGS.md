# Settings and Preferences

Settings rows and actions, the native Preferences window and its project context, Providers/Web search, Stats, notifications and bug reports.

## Agent conventions

- Settings → OpenCode's `OpenCodeLoginStartCard` (stable row anchor `#opencode-login-start`) presents **Start OpenCode at startup** as one lone-setting switch with a one-sentence **i** tip saying it starts when the user session opens; the switch is its state. It reads `GET /api/opencode/login-start` on mount and reconnect (the latest request wins) and changes it with `POST`, the switch disabled until the server answers. A refused change re-reads the state and shows one fixed, localized error under the row (`failed` or `unsupported-binary`); a failed read adds **Try again**; `unavailable` disables the switch with a caption. Runtime, artifacts and the replacement of the former supervision are in [OPENCODE_RUNTIME_SETUP.md](OPENCODE_RUNTIME_SETUP.md#start-opencode-at-login). Browser regression: `tests/browser/opencode-login-start.test.ts`.

- General offers `autoExpandActiveSubsessions` (default true): a new working/compacting/input chevron state opens visible branches belonging to the selected conversation, including its descendants at every depth (`dev-docs/UI_SHELL.md`). Disabling it leaves activity indicators and explicit navigation available; the preference is stored with the shared UI settings.

- The internal attachment reader uses the private native-parent transport, workspace/connection reservations and the scoped browser-participant owner. Its memory-only receipts qualify captured metadata freshness after publication owners have drained. Manifest reads are capped at 1 MiB before excess bytes are retained; private results have an 8-MiB allowance plus bounded protocol overhead before framing/JSON parsing. Read and current each receive five seconds, with monotonic expiry checked at settlement. Browser declarations contribute positive metadata through an authenticated, revocable stream capability. Publication rejects both raw query delimiters (`?` and `;`), including empty queries, before body parsing or capability admission. Full coverage stays unknown pending native live pre-mutation fencing and exhaustive project-use admission. The public Remotes disclosure's host removal closes known tabs, disconnects and forgets the server independently of these observations.

- Administrative GET projects the connection owner's private reservation state with the captured slot origin matched to current validated metadata and the displayed summary origin. An origin mismatch projects `unknown` while retaining the actual reservation count and captured connection lifetime. Credential presence remains origin-qualified. Lifecycle assertions belong to real acquisition/dispatch; metadata projection uses pure observations of slots, signals and local existing-connection state.

- Backend execution-server administration uses `GET /api/opencode-servers` and `POST /api/opencode-servers/probe`. Authentication, loopback/non-ingress peer identity, a configured/listener Host and trusted Origin/Fetch Metadata admit these routes before body parsing or native work. Native Electron/Tauri pages use their backend origin; authenticated host requests can omit browser headers. GET projects validated local-first metadata, live credential-presence booleans and the connection owner's current state (`connected`, `connecting`, `admitted_offline`, `disconnected`, `unknown`), with four explicit and one reserved local target. Reads use existing owners and authoritative app configuration. Probe accepts an unregistered `{ origin, credentials? }` candidate, retains credentials only during its operation and returns observed numeric release metadata or unavailable, negotiated feature states, `checkedAt` and fixed category/phase diagnostics. Administrative responses use `no-store`; diagnostics and request logs retain only fixed categories and redact complete bodies, paths and queries. The Remotes disclosure uses host-only `POST /api/opencode-servers/add` and `DELETE /api/opencode-servers/:id` for pairing and removal.

- Known-Form verification keeps its check control mounted and focusable during the read and after pending verification; `aria-disabled` accompanies a real action guard and the source status description. The Form editor composes verification with retained uncertainty from an earlier reply in one polite region. Pending native state leaves that earlier attempt uncertain; ordinary errors keep their alert. Source focus moved elsewhere stays with its new owner. Accepted placement transitions retire both in-flight checks and granted reply authority irreversibly, while same-placement metadata preserves them.

- Explicit live-only interruption coverage appears in the dock's accessible source disclosure: metadata-only server label plus stable ID (or ID alone), direction-isolated native directory and live-only limitation. Known stale drafts remain editable; response actions require a current correlated live request and matching capability snapshot, or an explicit bounded status check of that known Form with matching editor fields. A check preserves unknown project coverage and leaves stale permissions on their live-event gate. Terminal/indeterminate checks retain drafts, inert response controls and one polite source status; retries require another explicit gesture. Uncertain/superseded replies use one polite source-editor status through structured action identity; ordinary failures keep their alert treatment.

- `SettingsScreen` separates the accepted requested server from its resolved project context. Shared CodeNomad preferences stay usable while an unresolved, ambiguous, deleted or unknown project keeps native readers inactive. Qualified explicit catalogues read only native providers/models (and agents in Mission profile choices) on the captured project/Location; account, integration, Stats owner/cache/aggregation and depth readers mount only with local execution-settings admission. Capability changes and matching stream status revoke the context before inventory refresh; accepted request, binding and capability snapshot fence publication and retained handlers. Event-source epochs and service capability generations have independent owners. Preferences gives the event dispatcher its accepted request's server binding and releases deferred handshakes when that request changes, keeping event provenance independent of main-window hydration. The secondary renderer's setup observer waits for accepted local context. Keep unavailable sections selectable with persistent reasons and the selected server/folder in escaped, direction-isolated text.
- `LocalBackendSettings` identifies HOME files, profile environment and shared-service installation/binary maintenance as local backend controls. Explicit or unresolved project scopes require its deliberate local action before mounting those readers; the grant and callbacks belong to the exact accepted target. Shared Advanced behavior controls and Mission defaults remain available separately. Local catalogue/authentication flows retain existing credential integrations; explicit catalogue rendering mounts no authentication/account component. Read-only target selection and public server management/opening are owned by their separate delivery slices.
- The deliberate local action focuses its newly mounted, labelled control group; the next Tab enters its controls. Deferred focus checks the captured target's live grant and connected element. Initial mounting and external target changes preserve the window's focus ownership.
- `tests/browser/preferences-execution-scope.test.ts` measures Hebrew RTL long-target reflow in Chromium at 800×1200 CSS pixels and 400×600 CSS pixels with DPR 2 (the layout/raster equivalent of a 200% full-page zoom on that surface). Assertions compare target/reason/action rectangles with the actual visual viewport in CSS coordinates, exercise keyboard Tab/Enter and touch-enabled pointer dispatch, and save viewport captures and metrics under `.tmp/scr-1236/`. Native Electron/Tauri zoom, physical touch, screen-reader output and contrast require their own qualification.

- Preferences opened-folder constraints reject supplied empty, NUL-containing, oversized or wrongly typed paths at request admission; optional absent/null paths retain legacy absence. The URL fallback preserves a supplied path for validation. Lifecycle invalidation shares the resolver's opened-folder predicate and revokes context synchronously when a ready occurrence changes that folder, before its metadata refresh settles.

- Execution-backed settings admit the workspace's `executionSettings` capability before connection acquisition or local configuration/credential discovery. The shared plugin context covers activation, sources, image, web-search and native subagent-depth document reads/writes; image settings, subagent-depth settings and integrations also admit before their own acquisition. Provider account GET/PUT and service Stats (owner, cache and aggregation) share this local-only boundary. Explicit projects receive structured capability refusals; native chat catalogues retain their own admission.
- Three finer capabilities are also served by explicit servers. `plugins` admits plugin-inventory reads (`PluginControls.read`, integrations, MCP connect/disconnect through the explicit proxy); an explicit snapshot comes from native `config.get` + `plugin.list` with no write targets, so its switches are read-only, and every document read/write (activation, sources, images, web search, depth) keeps `executionSettings`. `providerUsage` admits the Usage route; an explicit project reads only native `/api/experimental/usage/limits` (OpenCode Go) and `session.stats` (Zen free estimate), never `credential.list`, host Claude Code files or provider APIs. `yolo` admits auto-accept (`dev-docs/NATIVE_INTERRUPTION_UX.md`). The UI-only `pluginWrite` feature hides plugin add/remove/update for explicit projects.
- Config files and filesystem discovery routes are explicitly host-only. Strict schemas reject `serverId`, `workspaceId` and binding selectors before filesystem access; Config files retains its fixed host allowlist. Project operations require their workspace identity instead of deriving authority from a path.

- Static execution-server config summaries conservatively report `hasCredentials: false`, `needsCredentials: true`; `SettingsService.getOpenCodeServerSummaries()` supplies the credential owner's live status. Schema preprocessing safely discards recognized development `credentialMode`/`credentialRef` fields and SettingsService normalizes valid metadata. The private per-instance credential Map is keyed by profile/config scope, server ID and origin; async mutations change memory synchronously, reads invalidate missing-server/different-origin entries, and clearing works after metadata removal. Registry changes clear credentials before URL retargeting, deletion or ID reuse; manager shutdown disposes the owner.

- `SettingsService.getOpenCodeServerRegistry()` is the writer for metadata at `config.server.opencodeServers`. Both generic config PATCH routes reject direct writes (including identical values), deletion and ancestor replacement that removes this subtree, before persistence/publication, for every caller. Ordinary settings patches preserve the profiles. The registry validates profile shapes and unique IDs; public config responses and owner/full-document events expose whitelisted metadata summaries. The backend persists pairing tokens and manual passwords in `opencode-server-pairings.json` (0600), scoped by profile/config, server ID and normalized origin. Restart reuses these secrets; expiry, HTTP 401, origin replacement and removal erase them. Live credential presence comes from the owning service. The shared connection owner aborts/fences captured old transports on rotation, deletion, disconnect and shutdown, including pending body preparation and returned streams. The home/launcher Remotes disclosure supplies host-only addition/removal and shared browsing/opening of registered servers. An absent registry implies the shared local profile without writing a migration.
- Settings → Providers separates Models, Web search and Images into three shared `.settings-disclosure` groups (no icons): Models starts open, Web search and Images folded, and a folded group mounts nothing, so its connection metadata, configuration contract and image-model catalog are read only once opened. Models and Web search each start with a provider selector, Connect action and configured-provider list; Web search then shows its global default and project override. Images (`opencode/image-settings.ts`, `settings/image-settings-card.tsx`, `styles/components/image-settings.css`) edits the Global document's `experimental.image_generate` and `experimental.media_blob`. OpenCode reads `image_generate` per field from the highest-priority document that sets it (unset means on, with the automatic model; only `false` turns the image tool off), but `media_blob` (like `subagent_depth`) from the whole `experimental` object of the highest-priority document that has one, so writing a project block would hide inherited experimental settings. The document that decides each value is read from the native configuration entries and reported under its control when it is not the Global one. When the selected Location's own project document (the project write target) decides `media_blob` through its existing `experimental` object, the snapshot names it under `mediaStorage.project` instead, the box shows the effective value and saving also writes `media_blob` there; the edit is refused if that object has disappeared, because creating one would hide inherited settings. The Missions depth editor's Inherit removes a project object left holding only that `media_blob` when it equals the Global one (`dev-docs/MISSIONS.md`); Off is written as `false`, because removing the key would expose a lower-priority document that enables it. When the fresh Global write target has no `experimental` object while a lower-priority document has one, creating it would hide that whole object (subagent depth, todos) from every Location without its own, even when the selected Location overrides it, so the group is read-only and the backend refuses the write; never copy the inherited values into the Global document instead. Each control appears only when the connected daemon's `Config.InfoEncoded` declares its key, because the native `experimental` object rejects unknown keys; never write either key without that capability. Image models come from native `GET /api/model?types=image` for the selected Location. Reuse provider rows, selectors, inputs and action styles; do not add an API-key disclosure or a separate card design. Search-only integrations stay out of the Models group. Web search configuration lives entirely here. Read connection metadata while this Settings surface is visible, never credential secret values; keep API-key entry explicit and clear drafts on context changes. Use the authorized Global/Project document operations shared with plugin controls and `opencode/native-setting-document.ts` for targeted JSONC edits. Preserve unrelated fields, native discovery roots, WSL atomic writes and conflict/connection/deletion fences. Group/search styling lives in `styles/components/websearch-settings.css`; credentials use native integration methods and remain global.
- Stats preferences explicitly aggregate the entire connected OpenCode service via `opencode/service-usage.ts`. Reserve the Usage label for the provider subscription panel. Native project IDs span independent clones, so never label native `session.stats` as physical-folder/Git-family scoped. Keep connection/workspace fences, `tools: "none"` and periods bounded to 366 days; never load transcripts for statistics or imply billing/quota precision. Last snapshots and period choices restore through backend-owned `state.ui.serviceUsage` (eight each/1 MiB, validated service/channel/folder identity), never a Preferences writer to main-window client state or a workspace-UUID cache. Native aggregation must not await optional discovery/cache reads; cached responses cannot replace fresh data. Backend authorized admission order, not completion order or client time, chooses the period across windows; optional publication is bounded and shutdown-fenced. Keep last-known-owner totals explicitly stale through disconnect/errors and revoke them on verified owner/discovery changes. Read while mounted and document-visible; hide cancels queued/trailing demand, activation revalidates once and terminal hints use the shared activity cooldown. Never treat document visibility as native minimize/occlusion detection or equate blur with hidden. See `dev-docs/CACHE_REFRESH_CONVENTIONS.md` for the remaining native scope. Styles live in `styles/components/usage-dashboard.css`.
- Settings rows keep only a title unless a caption is essential; secondary explanations go behind `components/settings/settings-info-tip.tsx` (a focusable "i" with a hover/focus tooltip that a tap toggles on touch screens, a span so it never becomes a row label's control or toggles it), styled in `styles/components/settings-info-tip.css`. An explanation that must end with a link uses `settings-info-link.tsx` instead: the same "i" as a button named by its text, opening a popover named by its `title` (click, Enter or Space; focus moves to the link; Escape or outside interaction closes it). Links to a setting use `openSettingsRow(section, row)` (`stores/settings-screen.ts`) with the row's stable `id` anchor (such as `#opencode-login-start`), never its label, and the link's text is the setting's own title key so it follows any rename; the row (`tabindex="-1"`) calls `useSettingsRowTarget` (`components/settings/settings-row-target.ts`) to claim the target once, focus itself and stay in view while the cards above load, and the embedded Settings dialog skips its own initial focus while the shown section holds the targeted row (`settingsRowPending`); closing Settings drops an unclaimed target. Hosts carry only the section to a native Preferences window, so the row travels as a 15-second same-origin `localStorage` hint that the window adopts for its active section on each request and on `storage` events (`adoptSettingsRowHint`). A link never reads or changes the linked setting. Behavior settings opt in with `infoKey` instead of `subtitleKey`. Folded settings groups use the one `.settings-disclosure` (`styles/components/settings-disclosure.css`; a summary may hold an inline heading that keeps the summary's look): Missions gathers every agent/model choice under "Agents and models" with the current request in its summary, and Advanced ends with the environment-variable editor folded under a single title.
- Settings update/install actions (OpenCode and Info), OpenCode's post-update service restart, and Remote Control start/pairing-link actions use the shared `.selector-button-primary` accent treatment. The shared `OpenCodeSetupPanel` keeps those same primary actions in startup recovery. Remote Control's header refresh is an icon-only `.window-icon-button`, retaining its localized accessible name, tooltip, disabled state and loading spinner.
- The native Preferences window never owns client state. Its General startup card (`settings/opener-startup-state-settings-card.tsx`) targets the exact local window that opened Preferences: the host records that opener and an epoch (Electron `PreferencesWindowRegistry`, Tauri `PreferencesWindow`), forwards only the fixed commands in `lib/native/startup-state-command.ts` to that renderer, which runs them through its own `stores/client-state` transitions. Mutations carry the displayed epoch and degrade to a read after the opener changes. Startup state is per window: when the opener is unknown (Preferences restored at launch) or closed, the host adopts the most recently used local window as the opener (`startupStateTargetId` + `adoptOpener` / `startup_state_target` + `set_opener`), rotating the epoch so a change prepared for another window is only a read. The card re-reads a few times while the adopted window starts and stays disabled only when no local window can answer.
- The native Preferences window shows no session, so it never reacts to session events: `stores/sessions.ts` wires the session event handlers (errors, TUI toasts, permissions, session and worktree updates) only outside it. A session alert, toast or notice therefore appears in the windows showing sessions and is acknowledged once there (`tests/browser/preferences-window.test.ts`).
- Native Preferences resolves its project context through `settings/preferences-project-context.ts` before Providers, Missions or Stats read project data. The optional request `serverId` qualifies every context, queue and asynchronous fence; absence selects `local-shared`, malformed explicit IDs are rejected and unknown IDs remain repairable unavailable targets. Both hosts validate and retain this field through open/reuse/get/accept and the strict client-state envelope; legacy requests retain serialized absence. The fallback URL reader accepts one `preferencesServerId` and rejects duplicate context selectors. Backend workspace IDs are ephemeral: accept an exact record only on the requested server and, when supplied, opened folder; otherwise bind only one unambiguous same-server folder match from the metadata-only inventory. Remote directories retain their exact spelling; local folders use `projectIdentity` normalization. Requests persist the opened folder as `workspacePath`, separate from the selected native `location.directory` (WSL/worktrees); keep the native directory for requests and drop any stale native workspace selector when rebinding. With an absent opened folder, an existing same-server occurrence keeps its selected Location; rebinding matches only that exact directory, never guessed translations or ancestors. Resolved context exposes read-only binding and capability metadata to settings consumers; execution-backed settings admission remains in the backend capability guards. A starting, missing or ambiguous project stays inactive. Read only on section demand, matching workspace lifecycle events or reconnect; never hydrate other workspaces, discover worktrees, create projects or poll. Record all deletion tombstones before filtering by the current binding so late inventory responses cannot publish deleted candidates, and revalidate when deletion resolves an ambiguity. Invalidation and newer native requests fence late reads, explicitly deleted occurrences never turn into sibling tabs, and rebinding persists through the existing Preferences request queue before publishing the execution context, preserving section and newer scrolling. The shared renderer and request contract cover both Electron and Tauri; regressions live in `tests/browser/preferences-startup.test.ts` and `preferences-window.test.ts`.
- Settings → Info's Support CodeNomad card, between Updates and Diagnostics, holds one `.selector-button-secondary` action that opens `helpUrl(locale, "sponsor")` through `openExternalUrl`, like the `open-sponsor` palette command and the native Help menu item; a failed opening shows the localized `commands.openSponsor.failed` alert in the card and is never replayed. Funding channels live only on the help site (`docs/help/funding.json`); never put payment links or amounts in the app.
- Settings → Info's Report a bug opens the `bug_report.yml` issue form with its text fields prefilled by id (`BUG_REPORT_FIELDS` in `lib/bug-report.ts`). When the template changes, keep those ids and their input/textarea types in sync: `lib/bug-report.test.ts` checks the repository's template. The section warms a bounded read of the form published on the default branch; the click never waits for it (WebKit drops user activation after about 1 s), using the settled assessment or else the form while a background read retries. Only a proven incompatible form (missing, unparsable, prefilled field removed or retyped) falls back to a blank issue carrying the same Markdown report; an unreachable read keeps the form. Never prefill listeners, addresses, paths, credentials or conversation data.
- Notification icon badges mirror the existing per-window bell/history unread count, never session status or native OS notification delivery. The browser favicon uses a dot; native Electron/Tauri hosts aggregate live primary-window counts and clear contributions on reload/close, keeping preferences and preview guests outside the badge authority. Keep UI projection in `lib/notification-icon-badge.ts` and host dispatch in `lib/native/notification-badge.ts`; do not add discovery scans or polling.
- Compaction notice claims use execution-server identity plus native durable position (or session/event ID), shared across project occurrences in each session window. Open bubbles replace only the same server/session's notice and expire through the existing handle lifetime; recent claims retain their bounded replay window. Notification category routing applies before retaining a displayed handle.
- Notifications have one routing table (`lib/notification-routing.ts`): every `showToastNotification` declares a category, and Settings → Notifications chooses per category On screen / History / System (`components/settings/notification-routing-table.tsx`, `styles/components/notification-routing.css`). The history, and therefore the icon badges, holds only what is routed there; errors always reach the screen and the history; `transient` live feedback (progress, retry countdowns, "up to date") stays on screen only. The routing table is the only system-notification control: checking a System box requests permission, and saved `osNotificationsEnabled`, `notifyOnNeedsInput` and `notifyOnIdle` preferences only seed the routing until it is first saved. The bell (tab bar, or title bar in the macOS desktop app) is the history, independent of system notifications. System delivery is held back only while the window has focus (visible and `document.hasFocus()`), unless **Notify when the app is focused** (`osNotificationsAllowWhenVisible`) is on; a window left open behind another application or on another screen still notifies (`tests/browser/system-notification-focus.test.ts`). Classify new notifications by what the user would want to find later, not by their source file; a warning that must be seen once by default (the incomplete-recovery warning) uses a category that shows a bubble (`projects`), never `needsInput`, whose default is System only.
